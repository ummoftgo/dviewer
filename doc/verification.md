## M35 — 텍스트·로그 가상 원문

생성기의 big.log는 정확히 17MiB·139,264줄이고 마지막 개행 없이 끝납니다. M34를 포함한 최종 매니페스트는 44검사·고유 파일 43개입니다. `textRawVirtual`은 표로 열린 것을 확인하고 실제 툴바로 원문 전환, 전체 줄 수·끝 스크롤·맨 위 복귀·마지막 내용 줄 검색과 강조·표 복귀를 검사합니다. 기존 reading.txt 검사는 CRLF를 정규화한 줄 내용과 줄 번호를 가상 원문 DOM에 대조합니다. 마크다운 스모크는 그대로입니다.

| vitest | rebase 후 266개(25파일) 통과 |

Rust 경계 검사는 LF·CRLF·끝 개행·빈 파일·BOM·UTF-16·조회 범위·반환 문자열 상한·Unicode 앞뒤 순환·취소·세대 폐기를 포함합니다. Svelte 자동 분석은 TextRawView의 issues가 없었습니다. 최초 sandbox 스모크는 창과 첫 결과를 만들지 못해 종료했고 같은 바이너리를 sandbox 밖에서 실행해 통과했습니다. 제품 코드는 바꾸지 않았습니다.

main의 M34(b6bba80) 위로 rebase하면서 문서와 스모크 진입점의 양쪽 변경을 보존했습니다. Rust 소스는 앞선 검증 때와 같아 전체 테스트와 clippy 결과를 재사용했고, 바뀐 프런트는 테스트·check·빌드 및 새 debug/release 스모크로 다시 확인했습니다.

release Rust 연산을 같은 바이트에 7회 반복한 중앙값입니다. 기존 원문 열은 doc_source_text와 같은 상한 확인·UTF-8 문자열 변환 뒤 줄 분할 연산이며 IPC·DOM 시간은 포함하지 않습니다. 표 색인은 같은 Records::Lines 코드를 앞뒤에서 실행한 대조군입니다. rebase 전 실제 WebView 전체 검사 시간은 reading.txt 111ms, big.log 497ms였으며 개별 검색 지연을 뜻하지 않습니다.

## M36 — 툴바 표 너비와 즉시 적용

기존 collectionWidths 검사에서 실제 툴바 드롭다운의 스크롤·채우기를 선택하고 체크 표시·현재 탭·설정 기본값·저장 호출을 확인한다. 현재 data-width-mode와 data-fitted 뒤 스크롤은 자연 폭, 채우기는 뷰포트 폭인지1px 허용으로 비교한다. 수동 조절을 모사한 폭·비율이 전환 시 재측정되는지도 확인한다. 저장 메서드만 일시 대체하여 사용자 스토어에 쓰지 않고 finally에서 원래 메서드와 상태를 복원한다. 기존 textReading에는 표에서 메뉴 표시·원문에서 숨김 단언을 추가한다. 검사 수는 늘리지 않는다.

vitest는 현재 탭 갱신·다른 탭 불변·설정 저장 경계와 자동 상한의 scroll→fill→scroll 왕복을 검사한다. 지정 변형은 적용 함수의 save 호출만 제거하여 저장 회귀가 실패하는지 확인한다. 키 조절 회귀는8px·Shift24px·fill 이웃 흡수·scroll 기준 폭 변경·최소64px를 검사한다. 맞춤 회귀는 fill 유지·이웃 최소 폭·내용이 가용폭 초과할 때 overflow·scroll 기준 폭 갱신·한 열 채우기를 확인한다. 컬렉션 스모크에서도 실제 그립의 초점·화살표·Enter와 더블클릭의 동일 맞춤을 확인한다.

## M34 — 컬렉션 격자 너비

sample.xlsx의 매출·비고 시트를 새 collectionWidths 검사 행에서 재사용한다. 매니페스트는43개 검사이며 고유 파일을 추가한 것은 아니다. 설정·탭 너비 방식·글꼴 크기·UI 배율을 명시하고 finally에서 복원한다. 실제 시트 선택기 전환 직후 기준 폭과 비율이 비워졌는지 확인하고, 선택한 시트의 통계·표본 폭·DOM 열 수·행·data-fitted 완료 뒤 머리글 폭과 뷰포트를1px 허용으로 대조한다. 각 시트의 헤더 메뉴에서 맞춤·추천·초기화가 있는지도 확인한다.

컬렉션 네 종류의 회귀는 설정 적재 전과 후의 값을 다르게 하여 공통 열기 경로가 적재 후의 너비 방식을 스냅샷으로 남기는지 검사한다. 별도 순수 회귀는 다음 시트의 페이지가 도착하기 전에 기준 폭과 비율을 함께 비우는지 확인한다. 지정 변형은 컬렉션에 설정 스냅샷을 적용하지 않도록 바꾸어 회귀가 실패하는지 검사한다.

## v0.17.0 CI 실패 수정 — 배분 완료·목차 반올림·부분 JSONL

2026-09-11, [실패한 CI run 34485778701](https://github.com/ummoftgo/dviewer/actions/runs/34485778701)의 중단된 조사를 재개했다. 검증 규칙 d02001e에 따라 cargo와 빌드를 순차 실행하고 각 최종 검사는 한 번 수행했다. Linux WebKit 재현은 추가하지 않았다.

**표는 하네스의 초기 배분 완료 대기가 빠진 문제로 분류했다.** `enhanceTables`는 `observer.observe(viewport)` 뒤 최초 `layout()`을 호출한다. 최초 폭이 없거나 표시되지 않으면 측정을 보류하며, 초기 ResizeObserver 통지가 `schedule(layout)`으로 후속 프레임의 배분을 예약한다. 자동 fill은 매번 intrinsic 측정과 `recommendWidths`로 들어가고 자연 폭을 `fillRatios`에 저장하는 경로가 없다. 기존 하네스는 반환 직후 observer의 첫 통지보다 먼저 너비를 읽고 실패하면 handle까지 폐기했다. 반환은 초기화 완료이지 모든 배분의 정착 완료가 아니었다.

검사는 폰트 준비 후 측정하고, 제품 observer보다 늦게 등록한 검사 observer의 양수 폭 통지와 그 뒤 예약된 프레임을 기다린다. 먼저 등록된 제품 observer가 예약한 배분이 완료된 뒤 실제/기대 너비를 한 번 비교한다. 올바른 너비가 나올 때까지 단언을 재시도하지 않는다. 같은 검사에서 최초 폭을 0으로 두었다가 정상 폭으로 바꾸어, 하네스의 refresh 없이 제품이 추천을 적용하는 경로도 확인한다. 제품의 표 배분 코드는 변경하지 않았다. 실패 메시지에는 실제/기대 너비와 적용된 col 너비를 남긴다.

CI 원본에는 실제 열 너비나 observer 통지 시각이 없으므로 그 실행에서 미준비를 유발한 환경 요인까지 재현했다고 주장하지 않는다. 이번 분류의 근거는 코드의 완료 계약과 지연 초기화 경로 검증이다. 이전 Windows CPU 제한 관측에서도 최초 적용 뒤 추천이 유지됐다.

**목차는 제품의 소수점 경계 결함이었다.** 이전 WebView2 CPU 제한 관측에서 스크롤이 정착한 뒤에도 대상 제목이 inset보다 조금 아래에 남아 이전 항목이 활성화됐다. 비교에 1 CSSpx를 허용하고 관측 좌표를 회귀 검사에 넣었다. 캐시 갱신이나 스크롤 프레임의 DOM 측정은 늘리지 않았다. 스모크도 클릭 중 잠깐 해당 항목을 통과한 상태로 종료하지 않고 scrollTop 정착 후 활성 항목을 다시 단언한다.

**JSONL은 하네스가 부분 줄을 파싱한 문제였다.** CI의 `waitForListening`은 실제로 `{"ok` 조각을 읽었고, 같은 분할 쓰기로 기존 파서의 SyntaxError를 재현했다. 이제 폴링 중에만 마지막 개행 뒤 조각을 보류한다. 종료 후 읽기와 완성된 잘못된 JSON은 계속 실패한다. Node 표준 테스트는 모든 분할 지점과 부분 summary, 손상된 완료 줄을 검사하며 CI의 세 OS에서 실행한다.

## v0.16.0 릴리스 스모크 — 닫힌 details 표의 완료 대기

[CI run 34371597314](https://github.com/ummoftgo/dviewer/actions/runs/34371597314)의 Windows·macOS는 `sample.md: markdownTables opened details table has invalid widths`로 실패했고 Linux는 통과했다. 제품의 조기 측정이 아니라 스모크의 조기 검증을 Windows WebView2에서 재현했다. 제품은 닫힌 표의 측정을 건너뛰고, `toggle`·`ResizeObserver` 뒤 예약한 프레임에서 너비를 적용한다. 스모크의 두 번째 프레임 콜백이 그 적용보다 먼저 실행될 수 있었다.

네이티브 추적에서 첫 프레임 1.0ms → ResizeObserver 1.4ms → toggle 5.1ms → 두 번째 프레임·검증 5.2ms 순서였고, 검증 시 두 열의 inline width는 빈 문자열이었다. 이후 표본에서는 둘 다 135.667px였다. 이는 적용 시각의 실측이 아니라 검증 전후 상태의 관측이다. [`toggle`은 비동기 작업](https://html.spec.whatwg.org/multipage/interactive-elements.html#the-details-element)이고 [ResizeObserver는 레이아웃 뒤 전달](https://www.w3.org/TR/resize-observer/#html-processing-model-event-loop)되므로 두 프레임 자체가 제품 콜백의 완료 신호는 아니다.

기존 스모크는 기본값이 `scroll`이면 연 뒤 `fill` 전환으로 동기 레이아웃을 실행해 경쟁을 가릴 수 있었다. 이제 닫힌 상태에서 `fill`로 맞춘 뒤 열고, 모든 열에 최초 너비가 적용됐을 때 기존 최솟값 검사를 한 번 수행한다. 완료 대기는 기존 제한 시간을 사용하며 올바른 너비가 나올 때까지 단언을 재시도하지 않는다. 제품 코드·사용자 동작은 바꾸지 않았다.

Linux CI는 Xvfb·D-Bus 안의 WebKitGTK이고 Windows는 WebView2, macOS는 WKWebView다. 같은 검사가 통과한 것은 다른 실행 순서에서 경쟁이 드러나지 않은 것으로 추정한다. CI 로그에는 프레임·toggle·observer 순서가 없어 Linux에서 어떤 콜백이 먼저였는지, 느림·포커스 중 무엇이 영향을 줬는지는 확정하지 않았다. Linux·macOS 재실행은 이번 로컬 검증에 포함하지 않았다.

배포키와 격리된 시험이다. 긴 명령은 백그라운드로 실행하고 결과를 파일에 남긴다. 먼저 실제 dviewer를 닫고 다음 스크립트로 두 버전의 개발 포터블·NSIS를 만든다. 버전·공개키·제품명·식별자는 설정 오버레이로만 주입한다.

```powershell
node scripts/test-updater-windows.mjs 0.13.0 0.14.0
node scripts/serve-updater-test.mjs
```

산출물은 `.agent-works/m22-e2e`이고 서버 주소는 그곳의 `server.json`에 기록된다. 시험키는 OS 임시 디렉터리에 있으며 내용은 출력하지 않는다. 서버는 별도 터미널/백그라운드로 유지하고 앱을 띄우는 셸에서 다음 환경을 설정한다.

```powershell
$probe = Join-Path $PWD '.agent-works/m22-e2e'
$server = Get-Content "$probe/server.json" | ConvertFrom-Json
```

1. 포터블 0.13.0 exe를 별도 디렉터리의 `dviewer.exe`로 복사해 실행한다. 설정의 배포 형태가 포터블인지, 시작 화면의 배지가 나오는지 확인한다.

## 프론트 테스트

`npm test` 는 vitest 를 돌립니다. 테스트는 검사하는 코드 **옆에** 삽니다(`src/**/*.test.ts`) — Rust 쪽 479개가 소스 옆 `#[cfg(test)]` 모듈에 있는 것과 같은 방식입니다.

**러너를 vitest 로 고른 이유는 하나뿐입니다: 이 저장소의 `vite.config.ts` 를 그대로 쓴다는 것.** 그래서 테스트가 앱과 **같은 방식으로 컴파일**되고, `.svelte.ts` 의 runes 가 추가 설정 없이 돕니다. 그것이 상태 로직을 테스트할 수 있게 하는 전부입니다. 설정은 `vitest.config.ts` 로 분리했습니다 — `vite.config.ts` 는 Tauri 빌드가 읽는 파일이라 테스트 전용 설정으로 불리지 않는 편이 안전합니다.

무엇을 덮는가:

- **순수 모듈**: `virtual.ts`(압축 스크롤 기하 — 상한 양쪽, 왕복, 0행·1행·높이 0), `source.ts`(탭이 같은 문서를 가리키는가), `archive/tree.ts`(목록 모양과 거르기), `grid/columns.ts`(문자 폭), `format.ts`, `keys.ts`.
- **상태 로직**: `docs.svelte.ts` 의 중복 방지 셋(파일·투명 해제·항목 재클릭), 여는 중 닫힌 탭의 문서 회수, `invalidate()` 의 리셋 목록, 검색 세대(seq) 가드, 빈 탭 규칙. `history.svelte.ts` 의 브라우저 의미.

**전부 과거에 실제로 났던 버그를 재현하는 형태입니다.** 그리고 각 항목이 정말 회귀를 잡는지는 그 자리를 일부러 깨뜨려 확인했습니다 — 아홉 군데(여는 중 닫힘 가드, 투명 해제 절, 번호 대신 이름 비교, 선택 노드 리셋, seq 증가, 거르기의 접힌 폴더 열기, 스페이서 상한, 넓은 문자 범위, 방문 중복 가드) 전부 테스트가 잡았습니다. 잡지 못하는 회귀 테스트는 테스트가 아닙니다.

**IPC 는 `vi.mock("../ipc")` 로 가립니다.** Tauri 의 `mockIPC` 는 `window.__TAURI_INTERNALS__` 를 갈아 끼우는 구현이라 DOM 환경이 필요한데, 그 의존을 목킹 편의로 들일 값이 아닙니다. 그리고 `ipc.ts` 가 이미 "백엔드와의 계약을 한 파일에 모은다"는 목적으로 존재하므로, 테스트가 가리는 경계도 거기가 맞습니다.

**컴포넌트 렌더 테스트(jsdom)는 들이지 않았습니다.** 가짜 DOM 에서 컴포넌트를 조립하는 것보다, 이 앱의 결합 구조(IPC·가상 스크롤)에는 진짜 창에서 진짜 IPC 로 도는 검증이 맞습니다. `test/setup.ts` 의 `localStorage` 스텁 열두 줄이 그 결정을 지키는 값입니다 — 여기에 두 번째 스텁이 필요해지면, 그건 그 상태 모듈이 상태이기를 그만두고 뷰가 되었다는 신호입니다.

## 스모크 하네스

`npm run smoke` 는 **앱을 실제로 띄워** 픽스처를 전부 열고, 어디까지 갔는지 기록합니다. 드라이버도 WebDriver 도 쓰지 않습니다 — 하네스가 곧 앱입니다(`--smoke` 플래그).

### 고전적 E2E 를 쓰지 않은 이유

이 저장소에서 **유닛 층을 빠져나간 결함의 실제 이력**을 보면 답이 나옵니다: 릴리스 빌드 한정 크래시(로그 빈 필드), 이벤트 루프 자기-블록 둘(`--new` 빈 창, 패널 검은 화면), capability 배선(opener 링크 전체 불능). 넷 다 **"띄우고 열면 터지는"** 계급이고 복잡한 상호작용이 필요 없었습니다. 반대로 사람 화면 확인 수십 항목이 잡은 상호작용 결함은 0건입니다 — 그 로직은 리뷰와 유닛 층이 먼저 잡았습니다.

WebDriver E2E 는 vitest 2층과 겹치는 것을 비싸게 다시 사면서(드라이버 드리프트·macOS 미지원·Linux webview ≠ WebView2·플레이크 유지비) 정작 위 계급을 더 잘 겨냥하지도 못합니다. 상호작용 회귀가 **실제로** 유닛 층을 빠져나가기 시작하면 그때 재론합니다.

### 모양

- **계획은 픽스처 옆에.** `gen-fixtures.mjs` 가 `fixtures/smoke.json` 을 함께 씁니다 — 무엇을 왜 만들었는지 아는 것은 생성기뿐이고, 기대값 없이 추가된 픽스처는 그 자리에서 눈에 띕니다(생성기가 없는 파일을 가리키면 오류로 알립니다).
- **`expect` 는 뷰 이름 한 칸**이거나 `error` 입니다. 그 한 칸이 아카이브의 두 동작을 가릅니다 — `single.zip` 은 문서 하나라 투명 해제되어야 하므로 `tree`, `single-locked.zip` 은 그 하나가 거절되어 목록으로 후퇴해야 하므로 `archive`.
- **결과는 JSON Lines, 한 줄씩 flush.** 끝에 한 번 쓰는 단일 문서는 이 하네스가 겨냥하는 바로 그 결함에서 빈 파일이 됩니다. 프로세스가 죽어도 **마지막 줄이 범인을 가리킵니다.** 요약 줄이 완주 표시이고, 그 부재가 곧 미완주 판정입니다.
- **시간 상한은 바깥에서.** 겨냥한 결함 셋 중 둘이 이벤트 루프가 안 도는 것이고, 안에 둔 타이머는 그 루프와 함께 멈춥니다.
- **종료 코드**: 0 전부 기대대로 · 1 하나 이상 어긋남 · 2 하네스가 시작하지 못함(매니페스트를 못 읽음, 결과를 못 씀).

### 무엇을 지나가는가

매니페스트의 37개를 **정상 열기 파이프라인 그대로** — `workspace.openPath` 를 부르고, 진짜 뷰가 마운트되어 스스로 로드하기를 기다립니다. 그 위에 파일 하나로는 닿지 않는 단계:

- `archive.zip` → `open_entry` 커맨드로 항목 열기 (클릭이 아니라 그 클릭이 부르는 것)
- `sample.csv` → 머리글 토글 뒤 검색 상태 초기화, 숫자 내림차순, 다른 열에서는 일치하지 않는 지정 열 필터, 원본 좌표 복사·표시 좌표 검색. 토글의 IPC와 상태 초기화를 하네스에서 호출하며 버튼 클릭 자체를 검증하지는 않습니다.
- `small.json` → `items`를 표로 펼쳐 컬렉션 뷰·열·값·0번 행을 확인하고, 재클릭 중복 방지와 부모를 닫은 뒤 자식 `grid_rows`의 `noSuchDoc` 거절을 검증합니다.
- `grid-cases.json` → 배열·맵·혼합·빈 값·긴 키·긴 값 조합의 화면 확인용 픽스처입니다.

그중 둘은 압축 **안**의 형식을 겨냥합니다. `workbook.zip` 과 `columnar.zip` 은 각각 xlsx 하나·parquet 하나만 든 zip 이라 투명 해제되고, 따라서 탭에 떠야 하는 것은 압축 목록이 아니라 시트 목록과 컬렉션입니다. 한때 `NeedsFile` 로 거절하던 자리이므로, 기대값 `collection` 이 곧 그 거절이 사라졌다는 진술입니다.

그리고 **단일 인스턴스 왕복** — 두 번째 프로세스를 실제로 띄워 ① 스스로 종료하는가 ② 첫 프로세스에 인자가 도착했는가, 그리고 `--new` 로 한 번 더 ③ 새 창이 정말 부팅해서 준 파일을 열었는가 ④ **그 창을 닫으면 그 창의 문서가 회수되는가.** 세 번째가 `--new` 빈 창 결함의 직접 재현이고, 네 번째는 단위 테스트가 닿을 수 없는 자리입니다 — 창 수명은 Tauri 이벤트 처리기 안이라 창이 실제로 파괴되어야 돌아갑니다. 그래서 그 창은 `smoke_done` 으로 나가지 않고 **스스로 닫고**, 처리기가 회수 결과를 한 줄 남기며 실행을 끝냅니다.

### 잡는지 확인했습니다

vitest 때와 같은 절차로, 두 가지를 일부러 깨뜨렸습니다: 매니페스트의 기대값을 틀리게 바꾸자 `sample.md: ready (prose 로 열림, tree 를 기대)`, `detect_kind` 에서 `md` 를 빼자 `sample.md: ready (table 로 열림, prose 를 기대)`. 둘 다 어느 픽스처가 어떻게 어긋났는지 이름을 댑니다.

### 프로세스 위생

스모크 프로세스는 플러그인 둘을 다르게 답니다. `window-state` 는 **양쪽 모드 모두 빼고** — 안 그러면 스모크가 사용자의 창 위치를 덮어씁니다. `single-instance` 는 **모드마다 반대로**입니다: 전수 열기는 빼야 하고(dviewer 가 떠 있으면 스모크가 그 창에 픽스처를 배달하고 죽습니다), 듣는 쪽은 있어야 합니다(단일 인스턴스가 되는 것이 시험 대상이므로). 그래서 듣는 쪽은 dviewer 가 이미 떠 있으면 성립하지 않고, 러너가 그 경우를 알아보고 그렇게 말합니다.

`--smoke` 는 **배포 바이너리에 남습니다.** 빌드 기능으로 가르면 배포된 것과 시험한 것이 다른 바이너리가 되어 이 하네스의 논거 절반이 사라집니다. 대신 `--smoke` 와 `--smoke-out` 둘 다 명시해야만 동작하고 기본값이 없어, 실수로 켜질 일도 임의 경로에 파일이 생길 일도 없습니다.

### CI

**태그 빌드(번들 잡)에서 릴리스 바이너리로 세 OS 전부** 돕니다. 검사 잡이 아닌 이유는 둘입니다 — 검사 잡은 앱 바이너리를 아예 만들지 않아 통째로 빌드가 하나 들어가고, 그건 디버그 빌드라 **이 하네스가 겨냥하는 "릴리스 빌드에서만 나는 크래시" 계급은 어차피 못 잡습니다.** Linux 러너는 화면이 없어 `xvfb-run` 으로 감쌉니다. 태그까지의 공백은 릴리스 절차의 "판올림 전 로컬 `npm run smoke` 1회"가 메웁니다. 검사 잡 편입은 디버그 빌드 시간을 CI 에서 실측한 뒤 결정합니다.

**검사 잡은 `cargo test` 앞에 픽스처를 만듭니다.** 그전까지는 만들지 않았고, 그래서 `xlsx` · `parquet` 의 **열한 개가 세 러너 모두에서 한 번도 돌지 않았습니다.** 그 테스트들은 픽스처가 없으면 `return` 으로 빠져나가 — 막 클론한 사람이 Node 를 깔기 전에도 `cargo test` 를 할 수 있게 하려는 거래입니다 — 아무것도 단언하지 않은 채 성공을 보고했습니다. 픽스처가 없으면 **통과하는** 테스트는 CI 에서는 테스트가 아닙니다.

두 읽기 다 필요하므로 어느 쪽인지를 짐작하지 않고 말하게 합니다. **`DVIEWER_FIXTURES=required`** 가 설정되어 있으면 픽스처 부재가 패닉이고(`src-tauri/src/testing.rs`), 없으면 지금처럼 조용히 비킵니다 — 로컬 동작은 그대로입니다. 검사 잡의 `cargo test` 에만 그 변수를 겁니다. Parquet 픽스처를 쓰는 예제는 번들 잡과 달리 `--release` 없이 돌립니다 — 이 잡에는 재사용할 릴리스 빌드가 없고, dev 프로필이면 바로 뒤 `cargo test` 가 컴파일할 것을 나눠 씁니다. 그리고 Node 가 세 러너 모두에 있어야 합니다 — 생성기가 `node:sqlite` 를 쓰므로 22.5+ 가 필요하고 러너 기본은 20 입니다.

잡는지도 두 방향으로 확인했습니다. `fixtures` 를 지우고 `DVIEWER_FIXTURES=required` 로 돌리면 **12개**가 붉어집니다 — 그 열한 개와, 같은 정책을 따르게 만든 헬퍼 자신의 테스트 하나. 변수 없이 같은 상태로 돌리면 전부 통과합니다.

`scripts/check-i18n.ts` 는 스크립트로 남습니다. 단언이 아니라 저장소 전체를 훑는 린트라 러너에 넣을 이유가 없습니다. 다만 사전 밖 문자열 스캔에서 `*.test.ts` 는 제외합니다 — 테스트 안의 한글은 화면 문자열이 아니라 **시험 대상 픽스처**(CP949 아카이브 이름, 한글로 재는 열 폭)이고, 사전 키를 요구하면 인코딩 경로를 영어로 시험하게 됩니다.

성능은 창 없이 직접 잽니다:

```bash
node scripts/gen-fixtures.mjs --huge
cd src-tauri
cargo run --release --example scan  -- ../fixtures/huge.json "needle:"
cargo run --release --example scan  -- ../fixtures/huge.xml  "항목 1499999"
cargo run --release --example jsonpath -- ../fixtures/huge.json
cargo run --release --example table -- ../fixtures/huge.csv  "항목 3999999"
cargo run --release --example table -- ../fixtures/huge.log  "id=1999999"
cargo run --release --example table -- ../fixtures/huge.jsonl "항목 1999999"
cargo run --release --example sqlite -- ../fixtures/huge.sqlite events
cargo run --release --example parquet -- read ../fixtures/huge.parquet "항목 1999999"
cargo run --release --example xlsx -- ../fixtures/huge.xlsx "9928527"
cargo run --release --example archive -- ../fixtures/archive.zip
```

이 저장소를 만든 기계(Windows 11)에서:

| 항목 | JSON 526MB | XML 184MB | CSV 298MB | 로그 208MB | JSONL 438MB |
|---|---|---|---|---|---|
| 규모 | 3,840만 노드 | 1,050만 노드 | 400만 행 × 12열 | 200만 행 × 4열 | 200만 행 × 7열 |
| 인덱싱 | 1.26초 (418 MB/s) | 0.97초 (190 MB/s) | 0.36초 (818 MB/s) | 0.21초 (1,004 MB/s) | 0.36초 (1,234 MB/s) |
| 인덱스 메모리 | 1.3 GB | 360 MB | 16 MB | 8 MB | 8 MB |
| 전체 펼치기 | 29ms | 7ms | — | — | — |
| 100행 조회 | 0.0ms | 0.0ms | 0.1ms | 0.0ms | 0.1ms |
| 본문 검색 | 1.16초 (48,000건) | 0.02초 | 0.05초 | 0.09초 | 0.02초 |
| 경로 검색 | 1.68초 | 0.51초 | — | — | — |
| 정규식 검색 | 1.73초 | — | 1.48초 | — | — |
| JSONPath (`$..notes`) | 0.06초 | — | — | — | — |

JSONPath 가 리터럴 검색보다 빠른 것이 이상해 보이지만 당연합니다 — 표현식은 단계마다 좁혀지므로 파일이 아니라 고른 것의 크기에 비례하고, 바이트를 훑지 않습니다. 이 값은 `..` 와 뒤따르는 단계를 하나로 읽은 뒤의 것으로, 그러기 전에는 2.26초였습니다(서브트리 전체를 모았다가 거르는 형태였습니다).

**선택자마다 값이 다릅니다.** 같은 파일(527MB·3,840만 노드)에서 `cargo run --release --example jsonpath -- ../fixtures/huge.json`, 세 번 돌려 안정된 값:

| 표현식 | 값 | 무엇을 치르는가 |
|---|---|---|
| `$.items[0]` | 16~21µs | 첫 자식 |
| `$.items[1000000]` | 5.7~6.0ms | 그 앞 백만 자식을 밟는다 |
| `$.items[-1]` | 14.0~14.8ms | 240만 자식 전부 |
| `$.items[1000000:1000010]` | 5.6~5.9ms | 열 개를 골라도 걷기는 한 번 |
| `$.items[0,1000000,-1]` | 19.3~19.8ms | 조각마다 한 번씩 |
| `$.items[?@.id > 2399990]` | **272ms** (M18 전 366) | 240만 후보에 질문 |
| `$..[?@.id > 2399990]` | **1.87초** (M18 전 2.62) | 3,840만 후보에 같은 질문 |
| `$..notes` | 65ms | 필터가 없어 M18 이 건드릴 것이 없다 |
| `$.items[?match(@.slug, 'item-23999[0-9]')]` | **322ms** (M18 전 531) | 240만 후보에 정규식 |
| `$.items[?length(@.slug) > 12]` | **310ms** (M18 전 458) | 정규식 없이 문자열만 — 0건이라 수집이 섞이지 않는다 |
| `$.items[?count(@.tags[*]) == 3]` | **386ms** (M18 전 522) | 후보마다 질의를 하나 더 |
| 취소 반응 | 244~275µs | 멈추라는 말에서 멈춤까지 |

읽히는 것 셋입니다. **뒤쪽에 닿는 것은 걷기**입니다 — 자식이 색인에서 이어 붙어 있어 n번째에 가려면 그 앞을 밟고, 그 행까지 스크롤하는 것과 같은 값입니다. **슬라이스는 그 걷기를 한 번만** 합니다(`[1000000:1000010]` 이 `[1000000]` 과 같은 값입니다). 그리고 **필터는 답이 아니라 파일을 따라갑니다** — 같은 아홉 건을 `$.items` 아래에서 0.35초, `$..` 아래에서 2.5초에 찾습니다. 그것이 이 한 단계에만 취소가 붙어 있는 이유이고, 4,096 노드마다 깃발을 보는 값이 0.3ms 입니다. **함수는 그 위에 얹힙니다** — 같은 240만 후보에 값 하나를 읽는 비교가 0.27초, 정규식이 0.32초, 후보마다 질의를 하나 더 푸는 `count()` 가 0.39초입니다. 정규식은 미리 컴파일해 두므로 여기서 재는 것은 컴파일이 아니라 맞춰 보는 값입니다.

**M18 이 후보당 할당을 걷어냈습니다**(괄호 안이 그 전 값입니다). 둘이었습니다 — 함수가 값을 `'static` 으로 돌려주려고 **문자열을 후보마다 복사**한 것, 그리고 `select_from` 이 단계마다 노드 id 목록을 **새로 만든** 것. 앞의 것은 수명을 꿰뚫어 없앴고(`length` 458 → 399ms), 뒤의 것은 버퍼를 돌려 쓰게 했습니다(기준 366 → 272ms).

**어느 행이 얼마나 줄었는지가 무엇을 고쳤는지 말해 줍니다.** `$..` 아래 필터가 가장 크게(-29%) 줄어든 것은 같은 질문을 3,840만 후보에 하므로 후보당 할당을 가장 여러 번 치르기 때문이고, `$..notes` 가 그대로인 것은 필터가 없어 후보당 반복 자체가 없기 때문입니다. 움직이지 않아야 할 행이 움직이지 않은 것이, 움직인 행의 숫자를 믿을 수 있게 합니다.

숫자들이 서로 다른 이유가 설계를 설명합니다. 로그와 CSV가 가장 빠르고 가벼운 건 레코드 시작 위치만 기록하기 때문이고(행당 4바이트), 로그가 그중에서도 빠른 건 따옴표 상태를 따라갈 필요가 없어 개행만 세면 되기 때문입니다. 로그의 열은 색인을 키우지 않습니다 — 배치는 앞부분 표본에서 한 번 정해지고, 칸 나누기는 화면에 보이는 행에서만 일어납니다, XML이 바이트당 가장 느린 건 같은 바이트 수에 노드가 훨씬 빽빽하기 때문입니다(마크업 18바이트당 노드 하나 대 JSON의 14바이트). 트리 인덱스 메모리는 파일 크기가 아니라 **노드 수**에 비례합니다(노드당 36바이트).

XML 경로의 위치 술어 `[n]` 은 따로 재야 합니다. 같은 이름 형제를 세는 일이고 그것은 선형인데, `tree_path` 가 **호버 팝오버**라 포인터가 지나는 행마다 다시 불립니다. `huge.xml`(184MB, `<catalog>` 아래 `<item>` 150만)의 마지막 자식에서:

| 방법 | 값 |
|---|---|
| 지름길(형제 번호를 순번으로) | 16~18µs |
| 걷기, 키를 `decode_key` 로 비교 | 60~62ms |
| 걷기, 바이트로 비교 | 11.2~11.4ms |

11ms 면 복사에는 안 보이지만 호버에는 보입니다 — 목록 위로 커서를 움직이면 스무 행에 220ms 입니다. 그래서 자식이 4,096을 넘으면 지름길을 쓰고, 그 지름길이 가정하는 것(앞선 속성 수·이름이 하나인가)만 싸게 확인합니다. 자세한 것은 [설계](architecture.md)의 XML 경로 절에 있습니다.

SQLite 는 이 표에 들어가지 않습니다. 바이트를 훑지 않으니 인덱싱 속도라는 항목 자체가 없고, 재는 것이 다릅니다 — 336MB·300만 행 `events` 테이블에서:

| 항목 | 값 |
|---|---|
| 연결 | 0.7ms |
| 컬렉션 훑기 (300만 행) | 0.33초 |
| 체크포인트 색인 | 22 KB |
| 60행 조회 (0행 / 150만 / 300만) | 0.16 / 0.16 / 0.15ms |
| 같은 조회, 색인 없이 `OFFSET` | 271ms |

마지막 두 줄이 체크포인트가 산 것입니다. SQLite 는 rowid 로는 즉시 찾아가지만 "300만 번째 행"이라는 개념이 없어서, 색인이 없으면 `OFFSET 2999940` 이 앞의 300만 행을 전부 밟고 지나갑니다 — **1,800배**. 1,024행마다 rowid 하나를 적어 두면 그것이 탐색 한 번과 1,023걸음 이내로 바뀌고, 300만 행에 22KB 를 씁니다.

rowid 가 없는 것 — 뷰와 WITHOUT ROWID 테이블 — 은 적어 둘 것이 없어 저 271ms 쪽 경로를 탑니다. 앞쪽은 똑같이 빠르고 뒤로 갈수록 느려집니다.

이미지로 읽을 때는 숫자가 달라집니다. 압축 항목과 내려받기가 그 길이고, 같은 파일을 `--bytes` 로 재서 나란히 놓으면(같은 기계·같은 예제이고, 파일 열은 다시 쟰 값이라 위 표와 오차 범위 안에서 같습니다):

| 항목 | 파일 | 이미지 |
|---|---|---|
| 연결 | 0.45ms | 0.34~0.52ms |
| 300만 행 훑기 | 332~339ms | 60~67ms |
| 색인 없이 끝 60행 | 286ms | 29ms |
| 60행 조회 | 160~183µs | 78~152µs |
| 전체 검색 | 1.0초 | 0.69~0.70초 |

**연결이 같은 급인 것이 요점입니다.** `sqlite3_deserialize` 는 `SQLITE_DESERIALIZE_READONLY` 로 버퍼를 제자리에서 읽으므로 여는 순간에 350MB 를 복사하지 않고, 복사했다면 여기서 드러났을 것입니다. 그 뒤가 더 빠른 것은 이미지 쪽에 파일 입출력이 아예 없기 때문이고, 그 대가는 **버퍼를 얻는 값** — 350MB 를 OS 캐시에서 읽는 데 70ms — 인데, 그것은 압축 파일이 이미 치른 값이므로 위 표에는 들어 있지 않습니다(예제가 그 읽기를 타이밍 밖에 둡니다). 이미지 전체가 메모리에 있다는 점은 바뀌지 않으므로, 압축 항목의 512MB 상한이 그대로 상한입니다.

JSONL 이 바이트당 가장 빠른 이유가 이 설계의 요약입니다. 색인은 개행만 세므로 로그와 같고, 값을 JSON 으로 읽는 일은 **화면에 있는 행에서만** 일어납니다. 100행에 0.1ms — 한 행당 1마이크로초 남짓이니, 행마다 스캐너를 도는 비용은 파일 크기와 무관하게 한 화면치입니다. 열을 알아내는 데는 앞 1MB 만 봅니다.

xlsx 는 표 밖입니다. 바이트를 훑는 것이 아니라 **통째로 변환**하기 때문입니다 — 재는 것이 인덱싱 속도가 아니라 "한 시트가 메모리에서 얼마가 되는가"입니다. 9.7MB·25만 행 × 6열(150만 칸) 파일에서:

| 항목 | 값 |
|---|---|
| 열기 (시트 목록) | 0.28ms — **이 픽스처의 고유 문자열이 13개**라서. 25만 개짜리 같은 크기 파일은 52ms. 파일에 처음 닿는 실행은 87ms(디스크 값) |
| 시트 선택 (값 전부) | 0.36초 |
| 메모리에 올라간 값 | **51MB** |
| 100행 조회 (앞 / 중간 / 끝) | 0.14 / 0.10 / 0.08ms |
| 수식 켜기, 처음 | 0.35초 (시트를 한 번 더 읽습니다) |
| 수식 켜기, 그다음 | 0.0002ms |
| 전체 검색 (150만 칸) | 0.18초 |

**9.7MB 가 51MB 가 됩니다 — 5.3배.** 이것이 64MB 상한이 있는 이유입니다. 공유 문자열은 디스크에서 색인 하나지만 메모리에서는 문자열 하나씩이고, 같은 비율이면 상한에 걸린 64MB 워크북은 340MB 쯤의 값이 됩니다.

**여는 값은 공유 문자열 표와 스타일이고, 시트 XML 은 고를 때 풉니다.** calamine 의 `Xlsx::new` 는 열 때 `read_shared_strings` · `read_styles` · `read_workbook` 을 전부 합니다. 그래서 여는 비용이 따라가는 것은 **행 수가 아니라 고유 문자열 수**입니다 — 이 표의 0.28ms 는 `huge.xlsx` 의 고유 문자열이 13개(머리글 여섯 · 거래처 다섯 · "정상"·"보류")뿐이라서 나온 값이고, 25만 행이 이름 다섯 개를 돌려 씁니다. 같은 25만 행을 **행마다 다른 이름**으로 써서(10.0MB, 고유 문자열 25만 개) 재면 여는 데 **52ms** 입니다. 실제 업무 파일은 이쪽에 가깝습니다.

같은 표의 이 자리에 한동안 **93ms** 가 적혀 있었는데, 그것은 파일에 처음 닿는 실행의 값입니다. 이번에 고친 코드로 재면서도 첫 실행은 87ms 였고 이어지는 실행은 전부 0.28ms 였습니다 — 같은 바이너리, 같은 파일. 그러니 옛 문장("여는 시간도 파일 크기를 따라갑니다")은 절반만 맞았습니다: 잰 값 93ms 는 9.7MB 를 처음 디스크에서 끌어오는 비용이었지만, 따라가는 것이 있다는 말 자체는 맞습니다 — 다만 따라가는 것은 파일 크기가 아니라 공유 문자열 표의 크기입니다.

**바이트로 읽게 바꾼 것이 값을 나쁘게 하지 않았습니다.** 같은 기계에서 바꾸기 전 커밋과 나란히 재면(`--release` 예제, 캐시가 덥혀진 뒤 세 번씩):

| 항목 | 전 | 후 |
|---|---|---|
| xlsx 열기 (9.7MB) | 0.37~0.42ms | 0.28~0.29ms |
| xlsx 열기 (2.9KB) | 0.38~1.84ms | 0.28~0.32ms |
| xlsx 시트 선택 | 341ms | 339ms |
| xlsx 전체 검색 | 173ms | 170ms |
| parquet 열기 (52MB) | 0.18~0.19ms | 0.17~0.18ms |
| parquet 새 행 그룹 조회 | 145~198ms | 143~191ms |
| parquet 전체 검색 | 2.5초 | 2.4초 |

여는 쪽이 조금 빨라진 것은 파일을 한 번 덜 열기 때문입니다 — 예전에는 이미 mmap 해 둔 파일을 리더가 경로로 한 번 더 열었습니다. `ChunkReader::get_bytes` 가 `Bytes::copy_from_slice` 로 복사하는데도 Parquet 쪽이 나빠지지 않은 이유는, 그것이 대신한 `File` 구현도 새 버퍼로 읽어 왔기 때문입니다. 그래서 `Bytes::from_owner` 로 복사를 없애는 쪽은 하지 않았습니다.

수식은 시트를 한 번 더 읽습니다. 값을 읽는 것과 같은 값(0.35초)이고, 그래서 켤 때만 읽습니다 — 두 번째부터는 들고 있는 것을 씁니다.

Parquet 도 표 밖입니다. 바이트를 훑지 않는 것은 SQLite 와 같은데, 이유가 하나 더 있습니다 — 파일이 **행 그룹 단위로 쓰여 있어** "통째로 안 올린다"를 형식이 공짜로 줍니다. 52MB·200만 행·행 그룹 8개(그룹당 25만 행)에서:

| 항목 | 값 |
|---|---|
| 열기 (푸터만) | 0.19ms — 311MB·행 그룹 48개에서도 0.61ms |
| 100행 조회, 새 행 그룹 | 147~194ms |
| 같은 조회, 캐시된 행 그룹 | 0.10ms |
| 전체 검색 (200만 행 × 5열) | 2.5초 |

**여는 시간이 파일 크기를 따라가지 않습니다.** 푸터의 색인만 읽으므로 자라는 것은 행 그룹 수뿐입니다 — 파일이 여섯 배(311MB)가 되고 행 그룹이 여섯 배(48개)가 되었을 때 0.19ms 가 0.61ms 가 됩니다. 그래서 다른 형식들이 가진 전체 상한이 여기엔 없습니다.

값을 치르는 자리는 하나뿐입니다 — 처음 닿는 행 그룹을 통째로 푸는 순간. 행 그룹은 형식이 쓰인 단위(페이지가 함께 압축되어 있어 절반만 풀 수 없습니다)라 피할 수 없고, 대신 **그 크기에만 상한**을 둡니다. 실측이 근거입니다: 5열 파일에서 그룹당 25만 행이 148ms, 100만 행이 608ms, 200만 행이 1.2초 — 행당 약 0.6µs 로 선형입니다. 상한 400만 행은 최악의 경우 2.5초쯤 창이 멈춘다는 뜻이고, 그보다 크면 뷰어가 아닙니다. 쓰는 쪽이 보통 10만~100만 행을 한 그룹에 넣으므로, 이 상한에 걸리는 것은 일부러 이상하게 쓴 파일뿐입니다.

행 그룹은 두 개까지 들고 있습니다. 뷰포트가 경계에 걸치면 둘이 필요하고, 셋째는 스크롤 방향이 바뀔 때만 값을 하는데 그때는 어차피 다시 읽힙니다.

YAML과 TOML은 이 표에 없습니다. 파서가 값을 메모리에 만들기 때문에 64MB에서 막아 두었고, 설정 파일이 사는 크기와는 자릿수가 다릅니다.

렌더링 결과를 눈으로 확인하려면:

```bash
cd src-tauri && cargo run --release --example render -- ../fixtures/sample.md out.html
```

인코딩은 실제 바이트로 확인합니다 — `cp949.csv`, `utf16.csv`, `utf8bom.csv` 를 열면 도구 모음이 각각 EUC-KR / UTF-16 LE / UTF-8 을 표시하고 세 파일 모두 `id | 이름 | 메모` 로 읽힙니다.

Parquet 픽스처만 생성기 밖에 있습니다. thrift 로 인코딩된 푸터 위에 압축된 열 덩어리라, 손으로 쓰는 것은 읽는 쪽을 시험하려고 형식을 다시 구현하는 일이 됩니다. 읽는 크레이트가 쓰기도 하므로 example 이 만듭니다:

```bash
cd src-tauri && cargo run --release --example parquet -- write ../fixtures [--huge]
```

압축 파일 쪽은 목록 만들기와 항목 하나 꺼내기를 잽니다:

```bash
cd src-tauri && cargo run --release --example archive -- ../fixtures/archive.zip 5
```

이 저장소를 만든 기계에서 목록 만들기 — 여는 값이 파일 크기가 아니라 항목 수를 따라간다는 것이 여기서 보입니다:

| 압축 파일 | 목록 |
|---|---|
| 1GB, 5,000 항목 (로컬 헤더가 기가바이트에 흩어짐) | 8.9ms |
| 8MB, 65,000 항목 | 52ms |
| 1GB, 65,000 항목 | 110ms |

프론트의 트리와 거르기는 10만 항목에서 만들기 78ms, 거르기 12ms 입니다 (거르기 입력에는 120ms 디바운스가 있습니다).

`fixtures/` 에는 형식마다 까다로운 부분을 담은 표본이 있습니다 — `sample.csv`(값 안의 쉼표·따옴표·개행, 짧은 행), `semicolon.csv`(확장자와 다른 구분자), `sample.xml`(속성·CDATA·주석·이름공간·혼합 내용·빈 요소), `sample.yaml`(앵커·여러 문서·문자열 아닌 키), `sample.toml`(날짜·배열 테이블), `wide.json`(루트 배열 100만), `deep.json`(깊이 500), `stream.jsonl`(중첩 객체·배열·null 이 섞인 레코드), `broken.json`(중간 절단), `sample.jsonc`(주석·후행 쉼표·문자열 안의 주석 표시, 그리고 **값 뒤의 덧말** 셋 — 닫는 괄호 뒤·한 줄에 둘·쉼표 뒤)와 그 엄격한 쌍둥이 `strict.json`, 확장자만 `.json` 인 `settings.json`, `sample.sqlite`(rowid 테이블·WITHOUT ROWID·뷰·BLOB·NULL 과 빈 문자열이 나란히), `sample.xlsx`(수식·날짜·시각만 든 칸·불리언·빈 칸·개행이 든 값, 그리고 **C4 에서 시작하는 둘째 시트**), `huge.xlsx`(공유 문자열이 메모리에서 부푸는 것을 재기 위한 25만 행), `sample.parquet`(**두 행씩 세 행 그룹** — 경계를 넘는 창을 잡으려고, 열 가운데의 NULL·타임스탬프·날짜·미리보기보다 긴 바이너리), `archive.zip`(json·log·md·csv·`.log.gz`·중첩 zip·잠김 플래그), `korean-names.zip`(플래그 없는 CP949 이름), `zip64.zip`(작지만 zip64 끝 레코드), `single.zip`·`single-locked.zip`(투명 해제가 되는 쪽과 목록으로 후퇴하는 쪽), `workbook.zip`·`columnar.zip`·`database.zip`(**압축 안의 통합 문서·컬럼 파일·데이터베이스** — 항목이 하나라 투명 해제되므로 뜨는 것은 압축 목록이 아니라 그 안쪽 형식이어야 합니다), 그리고 렌더링 기능을 한 번에 훑는 `sample.md`.

`sample.xlsx` 의 바이트는 `archive.zip` 의 `data/sales.xlsx` 와 `workbook.zip` 에도 그대로 들어갑니다. 같은 워크북을 파일로 한 번, 압축 항목으로 한 번 보내는 것이 요점입니다 — 다른 길로 왔을 뿐 같은 것이어야 합니다. `columnar.zip` 은 `sample.parquet` 과 같은 이유로 Rust 예제가 씁니다(생성기가 감쌀 대상을 만들지 못합니다). `sample.sqlite` 도 같습니다 — `archive.zip` 의 `data/app.sqlite` 와 `database.zip` 이 그 바이트입니다. `node:sqlite` 는 파일에만 쓰므로 쓴 뒤 다시 읽어 넣습니다.

## M19 — 배열·맵 격자와 정렬·필터

2026-09-06, Windows / Ryzen 9 9950X3D, Rust release 예제 기준이다. 단위 테스트는 픽스처 필수 모드로 세 번 실행한다. 화면 배치·머리글 조작·배율은 아래 자동 검증과 별도로 사용자 화면 확인이 필요하다.

clippy 전 값은 기준 커밋 `55fd756`을 별도 사본에서 실제 실행했다. 신규 경고는 정리했고 기존 경고는 범위 밖에 두었다. 스모크는 프런트와 `custom-protocol` 바이너리를 빌드한 뒤 저장소 루트에서 실행했다. 이 Windows 세션의 샌드박스 안에서는 WebView 자식이 시작되지 않아 결과 파일이 비어 있었고, 밖에서는 실행됐다. 밖에서 잡힌 짧은 CSV 행의 빈 칸 오류를 고친 뒤 전수와 왕복이 통과했다.

```powershell
# huge.jsonl / huge.sqlite / huge.xlsx / huge.parquet / wide.json도 같은 예제
```

백만 원소 배열의 추가 표 색인은 2.50ms, 4,000,000B였다(기존 트리 색인은 제외). 앞·중간·끝 원본 페이지는 같은 상수 시간 경로를 쓴다. Parquet은 310.5MiB·48개 행 그룹에서 앞·중간 100행이 530.1~548.3ms로 500ms를 넘었다. 최초 결정 측정에서도 556~580ms였으므로 머리글 정렬을 끄고 필터를 남겼다.

페이지 표는 앞·중간·끝의 두 번째·세 번째 조회 범위다. 원본 전·후가 대조군이며 첫 조회의 행 그룹 해제 비용은 별도 로그에 남긴다. 프로세스 실측은 열기·두 정렬·필터·페이지 조회 전체를 포함한 별도 실행이다. Working Set은 mmap과 캐시를 포함하고 Private는 100ms 간격 표본 최댓값이다. 아레나 256MiB는 전체 프로세스 메모리 상한이 아니다. Parquet 실험의 정렬 경로는 실제 UI에서 비활성화했다.
