## 프론트 테스트

`npm test` 는 vitest 를 돌립니다. 테스트는 검사하는 코드 **옆에** 삽니다(`src/**/*.test.ts`) — Rust 쪽 408개가 전부 같은 파일 안 `#[cfg(test)] mod tests` 에 있는 것과 같은 문법입니다.

**러너를 vitest 로 고른 이유는 하나뿐입니다: 이 저장소의 `vite.config.ts` 를 그대로 쓴다는 것.** 그래서 테스트가 앱과 **같은 방식으로 컴파일**되고, `.svelte.ts` 의 runes 가 추가 설정 없이 돕니다. 그것이 상태 로직을 테스트할 수 있게 하는 전부입니다. 설정은 `vitest.config.ts` 로 분리했습니다 — `vite.config.ts` 는 Tauri 빌드가 읽는 파일이라 테스트 전용 설정으로 불리지 않는 편이 안전합니다.

무엇을 덮는가:

- **순수 모듈**: `virtual.ts`(압축 스크롤 기하 — 상한 양쪽, 왕복, 0행·1행·높이 0), `source.ts`(탭이 같은 문서를 가리키는가), `archive/tree.ts`(목록 모양과 거르기), `grid/columns.ts`(문자 폭), `format.ts`, `keys.ts`.
- **상태 로직**: `docs.svelte.ts` 의 중복 방지 셋(파일·투명 해제·항목 재클릭), 여는 중 닫힌 탭의 문서 회수, `invalidate()` 의 리셋 목록, 검색 세대(seq) 가드, 빈 탭 규칙. `history.svelte.ts` 의 브라우저 의미.

**전부 과거에 실제로 났던 버그를 재현하는 형태입니다.** 그리고 각 항목이 정말 회귀를 잡는지는 그 자리를 일부러 깨뜨려 확인했습니다 — 아홉 군데(여는 중 닫힘 가드, 투명 해제 절, 번호 대신 이름 비교, 선택 노드 리셋, seq 증가, 거르기의 접힌 폴더 열기, 스페이서 상한, 넓은 문자 범위, 방문 중복 가드) 전부 테스트가 잡았습니다. 잡지 못하는 회귀 테스트는 테스트가 아닙니다.

**IPC 는 `vi.mock("../ipc")` 로 가립니다.** Tauri 의 `mockIPC` 는 `window.__TAURI_INTERNALS__` 를 갈아 끼우는 구현이라 DOM 환경이 필요한데, 그 의존을 목킹 편의로 들일 값이 아닙니다. 그리고 `ipc.ts` 가 이미 "백엔드와의 계약을 한 파일에 모은다"는 목적으로 존재하므로, 테스트가 가리는 경계도 거기가 맞습니다.

**컴포넌트 렌더 테스트(jsdom)는 들이지 않았습니다.** 가짜 DOM 에서 컴포넌트를 조립하는 것보다, 이 앱의 결합 구조(IPC·가상 스크롤)에는 진짜 창에서 진짜 IPC 로 도는 검증이 맞습니다. `test/setup.ts` 의 `localStorage` 스텁 열두 줄이 그 결정을 지키는 값입니다 — 여기에 두 번째 스텁이 필요해지면, 그건 그 상태 모듈이 상태이기를 그만두고 뷰가 되었다는 신호입니다.

## 스모크 하네스

`npm run smoke` 는 **앱을 실제로 띄워** 픽스처를 전부 열고, 어디까지 갔는지 기록합니다. 드라이버도 WebDriver 도 쓰지 않습니다 — 하네스가 곧 앱입니다(`--smoke` 플래그).

### 고전적 E2E 를 쓰지 않은 이유

이 저장소에서 **유닛 층을 빠져나간 결함의 실제 이력**을 보면 답이 나옵니다: 릴리스 빌드 한정 크래시(로그 빈 필드), 이벤트 루프 자기-블록 둘(`--new` 빈 창, 패널 검은 화면), capability 배선(opener 링크 전체 불능). 넷 다 **"띄우고 열면 터지는"** 계급이고 복잡한 상호작용이 필요 없었습니다. 반대로 사람 화면 확인 수십 항목이 잡은 상호작용 결함은 0건입니다 — 그 로직은 리뷰와 유닛 층이 먼저 잡았습니다.

WebDriver E2E 는 vitest 2층과 겹치는 것을 비싸게 다시 사면서(드라이버 드리프트·macOS 미지원·Linux webview ≠ WebView2·플레이크 유지비) 정작 위 계급을 더 잘 겨냥하지도 못합니다. 상호작용 회귀가 **실제로** 유닛 층을 빠져나가기 시작하면 그때 재론합니다.

### 모양

- **계획은 픽스처 옆에.** `gen-fixtures.mjs` 가 `fixtures/smoke.json` 을 함께 씁니다 — 무엇을 왜 만들었는지 아는 것은 생성기뿐이고, 기대값 없이 추가된 픽스처는 그 자리에서 눈에 띕니다(생성기가 없는 파일을 가리키면 오류로 알립니다).
- **`expect` 는 뷰 이름 한 칸**이거나 `error` 입니다. 그 한 칸이 아카이브의 두 동작을 가릅니다 — `single.zip` 은 문서 하나라 투명 해제되어야 하므로 `tree`, `single-locked.zip` 은 그 하나가 거절되어 목록으로 후퇴해야 하므로 `archive`.
- **결과는 JSON Lines, 한 줄씩 flush.** 끝에 한 번 쓰는 단일 문서는 이 하네스가 겨냥하는 바로 그 결함에서 빈 파일이 됩니다. 프로세스가 죽어도 **마지막 줄이 범인을 가리킵니다.** 요약 줄이 완주 표시이고, 그 부재가 곧 미완주 판정입니다.
- **시간 상한은 바깥에서.** 겨냥한 결함 셋 중 둘이 이벤트 루프가 안 도는 것이고, 안에 둔 타이머는 그 루프와 함께 멈춥니다.
- **종료 코드**: 0 전부 기대대로 · 1 하나 이상 어긋남 · 2 하네스가 시작하지 못함(매니페스트를 못 읽음, 결과를 못 씀).

### 무엇을 지나가는가

매니페스트의 34개를 **정상 열기 파이프라인 그대로** — `workspace.openPath` 를 부르고, 진짜 뷰가 마운트되어 스스로 로드하기를 기다립니다. 그 위에 파일 하나로는 닿지 않는 둘:

- `archive.zip` → `open_entry` 커맨드로 항목 열기 (클릭이 아니라 그 클릭이 부르는 것)
- `sample.csv` → 검색을 걸어 둔 채 머리글 토글 → 검색이 버려지는가. 이 로직은 컴포넌트 안(`TableView.applyShape`)에 있어 vitest 2층이 닿지 못하는 자리입니다.

그 33개 중 둘은 압축 **안**의 형식을 겨냥합니다. `workbook.zip` 과 `columnar.zip` 은 각각 xlsx 하나·parquet 하나만 든 zip 이라 투명 해제되고, 따라서 탭에 떠야 하는 것은 압축 목록이 아니라 시트 목록과 컬렉션입니다. 한때 `NeedsFile` 로 거절하던 자리이므로, 기대값 `collection` 이 곧 그 거절이 사라졌다는 진술입니다.

그리고 **단일 인스턴스 왕복** — 두 번째 프로세스를 실제로 띄워 ① 스스로 종료하는가 ② 첫 프로세스에 인자가 도착했는가, 그리고 `--new` 로 한 번 더 ③ 새 창이 정말 부팅해서 준 파일을 열었는가 ④ **그 창을 닫으면 그 창의 문서가 회수되는가.** 세 번째가 `--new` 빈 창 결함의 직접 재현이고, 네 번째는 단위 테스트가 닿을 수 없는 자리입니다 — 창 수명은 Tauri 이벤트 처리기 안이라 창이 실제로 파괴되어야 돌아갑니다. 그래서 그 창은 `smoke_done` 으로 나가지 않고 **스스로 닫고**, 처리기가 회수 결과를 한 줄 남기며 실행을 끝냅니다.

### 잡는지 확인했습니다

vitest 때와 같은 절차로, 두 가지를 일부러 깨뜨렸습니다: 매니페스트의 기대값을 틀리게 바꾸자 `sample.md: ready (prose 로 열림, tree 를 기대)`, `detect_kind` 에서 `md` 를 빼자 `sample.md: ready (table 로 열림, prose 를 기대)`. 둘 다 어느 픽스처가 어떻게 어긋났는지 이름을 댑니다.

### 프로세스 위생

스모크 프로세스는 플러그인 둘을 다르게 답니다. `window-state` 는 **양쪽 모드 모두 빼고** — 안 그러면 스모크가 사용자의 창 위치를 덮어씁니다. `single-instance` 는 **모드마다 반대로**입니다: 전수 열기는 빼야 하고(dviewer 가 떠 있으면 스모크가 그 창에 픽스처를 배달하고 죽습니다), 듣는 쪽은 있어야 합니다(단일 인스턴스가 되는 것이 시험 대상이므로). 그래서 듣는 쪽은 dviewer 가 이미 떠 있으면 성립하지 않고, 러너가 그 경우를 알아보고 그렇게 말합니다.

`--smoke` 는 **배포 바이너리에 남습니다.** 빌드 기능으로 가르면 배포된 것과 시험한 것이 다른 바이너리가 되어 이 하네스의 논거 절반이 사라집니다. 대신 `--smoke` 와 `--smoke-out` 둘 다 명시해야만 동작하고 기본값이 없어, 실수로 켜질 일도 임의 경로에 파일이 생길 일도 없습니다.

### CI

**태그 빌드(번들 잡)에서 릴리스 바이너리로 세 OS 전부** 돕니다. 검사 잡이 아닌 이유는 둘입니다 — 검사 잡은 앱 바이너리를 아예 만들지 않아 통째로 빌드가 하나 들어가고, 그건 디버그 빌드라 **이 하네스가 겨냥하는 "릴리스 빌드에서만 나는 크래시" 계급은 어차피 못 잡습니다.** Linux 러너는 화면이 없어 `xvfb-run` 으로 감쌉니다. 태그까지의 공백은 릴리스 절차의 "판올림 전 로컬 `npm run smoke` 1회"가 메웁니다. 검사 잡 편입은 디버그 빌드 시간을 CI 에서 실측한 뒤 결정합니다.

**검사 잡은 `cargo test` 앞에 픽스처를 만듭니다.** 그전까지는 만들지 않았고, 그래서 `xlsx` · `parquet` 의 **열한 개가 세 러너 모두에서 한 번도 돌지 않았습니다.** 그 테스트들은 픽스처가 없으면 `return` 으로 빠져나가 — 막 클론한 사람이 Node 를 깔기 전에도 `cargo test` 를 할 수 있게 하려는 거래입니다 — 아무것도 단언하지 않은 채 성공을 보고했습니다. 픽스처가 없으면 **통과하는** 테스트는 CI 에서는 테스트가 아닙니다.

두 읽기 다 필요하므로 어느 쪽인지를 짐작하지 않고 말하게 합니다. **`DVIEWER_FIXTURES=required`** 가 설정되어 있으면 픽스처 부재가 패닉이고(`src-tauri/src/testing.rs`), 없으면 지금처럼 조용히 비킵니다 — 로컬 동작은 그대로입니다. 검사 잡의 `cargo test` 에만 그 변수를 겁니다. Parquet 픽스처를 쓰는 예제는 번들 잡과 달리 `--release` 없이 돌립니다 — 이 잡에는 재사용할 릴리스 빌드가 없고, dev 프로필이면 바로 뒤 `cargo test` 가 컴파일할 것을 나눠 씁니다. 그리고 Node 가 세 러너 모두에 있어야 합니다 — 생성기가 `node:sqlite` 를 쓰므로 22.5+ 가 필요하고 러너 기본은 20 입니다.

잡는지도 두 방향으로 확인했습니다. `fixtures` 를 지우고 `DVIEWER_FIXTURES=required` 로 돌리면 **12개**가 붉어집니다 — 그 열한 개와, 같은 정책을 따르게 만든 헬퍼 자신의 테스트 하나. 변수 없이 같은 상태로 돌리면 전부 통과합니다.

`scripts/check-i18n.ts` 는 스크립트로 남습니다. 단언이 아니라 저장소 전체를 훑는 린트라 러너에 넣을 이유가 없습니다. 다만 사전 밖 문자열 스캔에서 `*.test.ts` 는 제외합니다 — 테스트 안의 한글은 화면 문자열이 아니라 **시험 대상 픽스처**(CP949 아카이브 이름, 한글로 재는 열 폭)이고, 사전 키를 요구하면 인코딩 경로를 영어로 시험하게 됩니다.

성능은 창 없이 직접 잽니다:

```bash
node scripts/gen-fixtures.mjs --huge
cd src-tauri
cargo run --release --example scan  -- ../fixtures/huge.json "needle:"
cargo run --release --example scan  -- ../fixtures/huge.xml  "항목 1499999"
cargo run --release --example jsonpath -- ../fixtures/huge.json
cargo run --release --example table -- ../fixtures/huge.csv  "항목 3999999"
cargo run --release --example table -- ../fixtures/huge.log  "id=1999999"
cargo run --release --example table -- ../fixtures/huge.jsonl "항목 1999999"
cargo run --release --example sqlite -- ../fixtures/huge.sqlite events
cargo run --release --example parquet -- read ../fixtures/huge.parquet "항목 1999999"
cargo run --release --example xlsx -- ../fixtures/huge.xlsx "9928527"
cargo run --release --example archive -- ../fixtures/archive.zip
```

**선택자마다 값이 다릅니다.** 같은 파일(527MB·3,840만 노드)에서 `cargo run --release --example jsonpath -- ../fixtures/huge.json`, 세 번 돌려 안정된 값:

| `$.items[?count(@.tags[*]) == 3]` | 505~512ms | 후보마다 질의를 하나 더 |
| 취소 반응 | 259~313µs | 멈추라는 말에서 멈춤까지 |

읽히는 것 셋입니다. **뒤쪽에 닿는 것은 걷기**입니다 — 자식이 색인에서 이어 붙어 있어 n번째에 가려면 그 앞을 밟고, 그 행까지 스크롤하는 것과 같은 값입니다. **슬라이스는 그 걷기를 한 번만** 합니다(`[1000000:1000010]` 이 `[1000000]` 과 같은 값입니다). 그리고 **필터는 답이 아니라 파일을 따라갑니다** — 같은 아홉 건을 `$.items` 아래에서 0.35초, `$..` 아래에서 2.5초에 찾습니다. 그것이 이 한 단계에만 취소가 붙어 있는 이유이고, 4,096 노드마다 깃발을 보는 값이 0.3ms 입니다. **함수는 그 위에 얹힙니다** — 같은 240만 후보에 값 하나를 읽는 비교가 0.35초, 정규식이 0.52초, 후보마다 질의를 하나 더 푸는 `count()` 가 0.51초입니다. 정규식은 미리 컴파일해 두므로 여기서 재는 것은 컴파일이 아니라 맞춰 보는 값입니다.

숫자들이 서로 다른 이유가 설계를 설명합니다. 로그와 CSV가 가장 빠르고 가벼운 건 레코드 시작 위치만 기록하기 때문이고(행당 4바이트), 로그가 그중에서도 빠른 건 따옴표 상태를 따라갈 필요가 없어 개행만 세면 되기 때문입니다. 로그의 열은 색인을 키우지 않습니다 — 배치는 앞부분 표본에서 한 번 정해지고, 칸 나누기는 화면에 보이는 행에서만 일어납니다, XML이 바이트당 가장 느린 건 같은 바이트 수에 노드가 훨씬 빽빽하기 때문입니다(마크업 18바이트당 노드 하나 대 JSON의 14바이트). 트리 인덱스 메모리는 파일 크기가 아니라 **노드 수**에 비례합니다(노드당 36바이트).

XML 경로의 위치 술어 `[n]` 은 따로 재야 합니다. 같은 이름 형제를 세는 일이고 그것은 선형인데, `tree_path` 가 **호버 팝오버**라 포인터가 지나는 행마다 다시 불립니다. `huge.xml`(184MB, `<catalog>` 아래 `<item>` 150만)의 마지막 자식에서:

| 방법 | 값 |
|---|---|
| 지름길(형제 번호를 순번으로) | 16~18µs |
| 걷기, 키를 `decode_key` 로 비교 | 60~62ms |
| 걷기, 바이트로 비교 | 11.2~11.4ms |

11ms 면 복사에는 안 보이지만 호버에는 보입니다 — 목록 위로 커서를 움직이면 스무 행에 220ms 입니다. 그래서 자식이 4,096을 넘으면 지름길을 쓰고, 그 지름길이 가정하는 것(앞선 속성 수·이름이 하나인가)만 싸게 확인합니다. 자세한 것은 [설계](architecture.md)의 XML 경로 절에 있습니다.

SQLite 는 이 표에 들어가지 않습니다. 바이트를 훑지 않으니 인덱싱 속도라는 항목 자체가 없고, 재는 것이 다릅니다 — 336MB·300만 행 `events` 테이블에서:

| 항목 | 값 |
|---|---|
| 연결 | 0.7ms |
| 컬렉션 훑기 (300만 행) | 0.33초 |
| 체크포인트 색인 | 22 KB |
| 60행 조회 (0행 / 150만 / 300만) | 0.16 / 0.16 / 0.15ms |
| 같은 조회, 색인 없이 `OFFSET` | 271ms |

마지막 두 줄이 체크포인트가 산 것입니다. SQLite 는 rowid 로는 즉시 찾아가지만 "300만 번째 행"이라는 개념이 없어서, 색인이 없으면 `OFFSET 2999940` 이 앞의 300만 행을 전부 밟고 지나갑니다 — **1,800배**. 1,024행마다 rowid 하나를 적어 두면 그것이 탐색 한 번과 1,023걸음 이내로 바뀌고, 300만 행에 22KB 를 씁니다.

rowid 가 없는 것 — 뷰와 WITHOUT ROWID 테이블 — 은 적어 둘 것이 없어 저 271ms 쪽 경로를 탑니다. 앞쪽은 똑같이 빠르고 뒤로 갈수록 느려집니다.

이미지로 읽을 때는 숫자가 달라집니다. 압축 항목과 내려받기가 그 길이고, 같은 파일을 `--bytes` 로 재서 나란히 놓으면(같은 기계·같은 예제이고, 파일 열은 다시 쟰 값이라 위 표와 오차 범위 안에서 같습니다):

| 항목 | 파일 | 이미지 |
|---|---|---|
| 연결 | 0.45ms | 0.34~0.52ms |
| 300만 행 훑기 | 332~339ms | 60~67ms |
| 색인 없이 끝 60행 | 286ms | 29ms |
| 60행 조회 | 160~183µs | 78~152µs |
| 전체 검색 | 1.0초 | 0.69~0.70초 |

**연결이 같은 급인 것이 요점입니다.** `sqlite3_deserialize` 는 `SQLITE_DESERIALIZE_READONLY` 로 버퍼를 제자리에서 읽으므로 여는 순간에 350MB 를 복사하지 않고, 복사했다면 여기서 드러났을 것입니다. 그 뒤가 더 빠른 것은 이미지 쪽에 파일 입출력이 아예 없기 때문이고, 그 대가는 **버퍼를 얻는 값** — 350MB 를 OS 캐시에서 읽는 데 70ms — 인데, 그것은 압축 파일이 이미 치른 값이므로 위 표에는 들어 있지 않습니다(예제가 그 읽기를 타이밍 밖에 둡니다). 이미지 전체가 메모리에 있다는 점은 바뀌지 않으므로, 압축 항목의 512MB 상한이 그대로 상한입니다.

JSONL 이 바이트당 가장 빠른 이유가 이 설계의 요약입니다. 색인은 개행만 세므로 로그와 같고, 값을 JSON 으로 읽는 일은 **화면에 있는 행에서만** 일어납니다. 100행에 0.1ms — 한 행당 1마이크로초 남짓이니, 행마다 스캐너를 도는 비용은 파일 크기와 무관하게 한 화면치입니다. 열을 알아내는 데는 앞 1MB 만 봅니다.

xlsx 는 표 밖입니다. 바이트를 훑는 것이 아니라 **통째로 변환**하기 때문입니다 — 재는 것이 인덱싱 속도가 아니라 "한 시트가 메모리에서 얼마가 되는가"입니다. 9.7MB·25만 행 × 6열(150만 칸) 파일에서:

| 항목 | 값 |
|---|---|
| 열기 (시트 목록) | 0.28ms — **이 픽스처의 고유 문자열이 13개**라서. 25만 개짜리 같은 크기 파일은 52ms. 파일에 처음 닿는 실행은 87ms(디스크 값) |
| 시트 선택 (값 전부) | 0.36초 |
| 메모리에 올라간 값 | **51MB** |
| 100행 조회 (앞 / 중간 / 끝) | 0.14 / 0.10 / 0.08ms |
| 수식 켜기, 처음 | 0.35초 (시트를 한 번 더 읽습니다) |
| 수식 켜기, 그다음 | 0.0002ms |
| 전체 검색 (150만 칸) | 0.18초 |

**9.7MB 가 51MB 가 됩니다 — 5.3배.** 이것이 64MB 상한이 있는 이유입니다. 공유 문자열은 디스크에서 색인 하나지만 메모리에서는 문자열 하나씩이고, 같은 비율이면 상한에 걸린 64MB 워크북은 340MB 쯤의 값이 됩니다.

**여는 값은 공유 문자열 표와 스타일이고, 시트 XML 은 고를 때 풉니다.** calamine 의 `Xlsx::new` 는 열 때 `read_shared_strings` · `read_styles` · `read_workbook` 을 전부 합니다. 그래서 여는 비용이 따라가는 것은 **행 수가 아니라 고유 문자열 수**입니다 — 이 표의 0.28ms 는 `huge.xlsx` 의 고유 문자열이 13개(머리글 여섯 · 거래처 다섯 · "정상"·"보류")뿐이라서 나온 값이고, 25만 행이 이름 다섯 개를 돌려 씁니다. 같은 25만 행을 **행마다 다른 이름**으로 써서(10.0MB, 고유 문자열 25만 개) 재면 여는 데 **52ms** 입니다. 실제 업무 파일은 이쪽에 가깝습니다.

같은 표의 이 자리에 한동안 **93ms** 가 적혀 있었는데, 그것은 파일에 처음 닿는 실행의 값입니다. 이번에 고친 코드로 재면서도 첫 실행은 87ms 였고 이어지는 실행은 전부 0.28ms 였습니다 — 같은 바이너리, 같은 파일. 그러니 옛 문장("여는 시간도 파일 크기를 따라갑니다")은 절반만 맞았습니다: 잰 값 93ms 는 9.7MB 를 처음 디스크에서 끌어오는 비용이었지만, 따라가는 것이 있다는 말 자체는 맞습니다 — 다만 따라가는 것은 파일 크기가 아니라 공유 문자열 표의 크기입니다.

**바이트로 읽게 바꾼 것이 값을 나쁘게 하지 않았습니다.** 같은 기계에서 바꾸기 전 커밋과 나란히 재면(`--release` 예제, 캐시가 덥혀진 뒤 세 번씩):

| 항목 | 전 | 후 |
|---|---|---|
| xlsx 열기 (9.7MB) | 0.37~0.42ms | 0.28~0.29ms |
| xlsx 열기 (2.9KB) | 0.38~1.84ms | 0.28~0.32ms |
| xlsx 시트 선택 | 341ms | 339ms |
| xlsx 전체 검색 | 173ms | 170ms |
| parquet 열기 (52MB) | 0.18~0.19ms | 0.17~0.18ms |
| parquet 새 행 그룹 조회 | 145~198ms | 143~191ms |
| parquet 전체 검색 | 2.5초 | 2.4초 |

여는 쪽이 조금 빨라진 것은 파일을 한 번 덜 열기 때문입니다 — 예전에는 이미 mmap 해 둔 파일을 리더가 경로로 한 번 더 열었습니다. `ChunkReader::get_bytes` 가 `Bytes::copy_from_slice` 로 복사하는데도 Parquet 쪽이 나빠지지 않은 이유는, 그것이 대신한 `File` 구현도 새 버퍼로 읽어 왔기 때문입니다. 그래서 `Bytes::from_owner` 로 복사를 없애는 쪽은 하지 않았습니다.

수식은 시트를 한 번 더 읽습니다. 값을 읽는 것과 같은 값(0.35초)이고, 그래서 켤 때만 읽습니다 — 두 번째부터는 들고 있는 것을 씁니다.

Parquet 도 표 밖입니다. 바이트를 훑지 않는 것은 SQLite 와 같은데, 이유가 하나 더 있습니다 — 파일이 **행 그룹 단위로 쓰여 있어** "통째로 안 올린다"를 형식이 공짜로 줍니다. 52MB·200만 행·행 그룹 8개(그룹당 25만 행)에서:

| 항목 | 값 |
|---|---|
| 열기 (푸터만) | 0.19ms — 311MB·행 그룹 48개에서도 0.61ms |
| 100행 조회, 새 행 그룹 | 147~194ms |
| 같은 조회, 캐시된 행 그룹 | 0.10ms |
| 전체 검색 (200만 행 × 5열) | 2.5초 |

**여는 시간이 파일 크기를 따라가지 않습니다.** 푸터의 색인만 읽으므로 자라는 것은 행 그룹 수뿐입니다 — 파일이 여섯 배(311MB)가 되고 행 그룹이 여섯 배(48개)가 되었을 때 0.19ms 가 0.61ms 가 됩니다. 그래서 다른 형식들이 가진 전체 상한이 여기엔 없습니다.

값을 치르는 자리는 하나뿐입니다 — 처음 닿는 행 그룹을 통째로 푸는 순간. 행 그룹은 형식이 쓰인 단위(페이지가 함께 압축되어 있어 절반만 풀 수 없습니다)라 피할 수 없고, 대신 **그 크기에만 상한**을 둡니다. 실측이 근거입니다: 5열 파일에서 그룹당 25만 행이 148ms, 100만 행이 608ms, 200만 행이 1.2초 — 행당 약 0.6µs 로 선형입니다. 상한 400만 행은 최악의 경우 2.5초쯤 창이 멈춘다는 뜻이고, 그보다 크면 뷰어가 아닙니다. 쓰는 쪽이 보통 10만~100만 행을 한 그룹에 넣으므로, 이 상한에 걸리는 것은 일부러 이상하게 쓴 파일뿐입니다.

행 그룹은 두 개까지 들고 있습니다. 뷰포트가 경계에 걸치면 둘이 필요하고, 셋째는 스크롤 방향이 바뀔 때만 값을 하는데 그때는 어차피 다시 읽힙니다.

YAML과 TOML은 이 표에 없습니다. 파서가 값을 메모리에 만들기 때문에 64MB에서 막아 두었고, 설정 파일이 사는 크기와는 자릿수가 다릅니다.

렌더링 결과를 눈으로 확인하려면:

```bash
cd src-tauri && cargo run --release --example render -- ../fixtures/sample.md out.html
```

인코딩은 실제 바이트로 확인합니다 — `cp949.csv`, `utf16.csv`, `utf8bom.csv` 를 열면 도구 모음이 각각 EUC-KR / UTF-16 LE / UTF-8 을 표시하고 세 파일 모두 `id | 이름 | 메모` 로 읽힙니다.

Parquet 픽스처만 생성기 밖에 있습니다. thrift 로 인코딩된 푸터 위에 압축된 열 덩어리라, 손으로 쓰는 것은 읽는 쪽을 시험하려고 형식을 다시 구현하는 일이 됩니다. 읽는 크레이트가 쓰기도 하므로 example 이 만듭니다:

```bash
cd src-tauri && cargo run --release --example parquet -- write ../fixtures [--huge]
```

압축 파일 쪽은 목록 만들기와 항목 하나 꺼내기를 잽니다:

```bash
cd src-tauri && cargo run --release --example archive -- ../fixtures/archive.zip 5
```

이 저장소를 만든 기계에서 목록 만들기 — 여는 값이 파일 크기가 아니라 항목 수를 따라간다는 것이 여기서 보입니다:

| 압축 파일 | 목록 |
|---|---|
| 1GB, 5,000 항목 (로컬 헤더가 기가바이트에 흩어짐) | 8.9ms |
| 8MB, 65,000 항목 | 52ms |
| 1GB, 65,000 항목 | 110ms |

프론트의 트리와 거르기는 10만 항목에서 만들기 78ms, 거르기 12ms 입니다 (거르기 입력에는 120ms 디바운스가 있습니다).
