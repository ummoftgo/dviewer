## 설계 요약

무거운 작업은 전부 Rust에 있고, 프론트엔드는 화면에 보이는 만큼만 그립니다.

### JSON: 왜 이렇게까지 하는가

500MB JSON을 `serde_json::Value` 로 파싱하면 힙이 수 GB로 부풉니다. 대신:

1. **바이트 스캐너** (`src-tauri/src/tree/scanner.rs`) 가 mmap된 원본을 한 번만 훑으며 노드당 36바이트짜리 평면 인덱스를 만듭니다. 노드는 DFS 선행순서로 나열되므로 **노드 id 순서 = 바이트 순서**이고, 이후 모든 단계가 이 불변식 위에 서 있습니다.
2. **가시성 관리** (`tree/index.rs`) 는 노드당 1비트 + 4096노드 단위 블록 카운트입니다. "N번째 보이는 행이 어느 노드인가"는 블록 카운터를 훑고 블록 안에서 popcount 하면 끝이고, 접기는 비트 범위를 지우고 영향받은 블록만 다시 세면 됩니다. Fenwick 트리는 조회가 빠른 대신 접기가 비싸고, 단순 플래그 배열은 그 반대입니다.
3. **뷰포트 조회** (`tree/mod.rs`) 는 보이는 100여 행만 반환하고 값은 500자에서 자릅니다. 파일 크기와 무관하게 IPC 페이로드는 수 KB입니다.
4. **검색** (`tree/search.rs`) 은 원본 바이트를 aho-corasick으로 훑고, `val_start` 가 노드 순서로 단조 증가한다는 점을 이용해 이진 탐색으로 매치를 노드에 되돌립니다.

**경로 검색**은 다릅니다. 경로는 파일 어디에도 없고 트리에서 파생되는 값이라 바이트 스캔으로 찾을 수 없습니다. 대신 선행순서로 나열된 노드 배열을 훑으며 버퍼 하나를 재사용합니다 — 부모 길이까지 자르고 자기 세그먼트만 덧붙이는 식이라, 노드마다 문자열을 만들지 않습니다. 두 가지 성질이 비용을 낮춥니다: 조상이 이미 일치하면 그 하위 전체가 일치하므로 다시 찾지 않고, 아니라면 접두사는 불일치가 확정이므로 **새로 붙인 꼬리만** 훑으면 됩니다. 덕분에 노드당 비용이 경로 깊이가 아니라 검색어 길이에 비례합니다.

인덱싱과 검색은 백그라운드 스레드에서 돌고 진행률·결과를 이벤트로 흘려보냅니다. 탭을 닫으면 취소됩니다.

### 열세 형식, 네 개의 읽는 방식

형식마다 뷰를 만들면 열세 벌이 되고 열두 벌은 늘 뒤처집니다. 그래서 형식은 **어떻게 읽히는가**로 묶습니다. 프론트엔드는 `DocKind` 가 아니라 `DocView`(`prose` / `tree` / `table` / `collection`)로 분기합니다.

트리로 가는 네 형식은 각자 다른 방식으로 도착합니다. 모듈 이름이 `tree` 인 것도 그래서입니다 — 한때 `json` 이었지만 넷을 담당하게 된 뒤로는 형식이 아니라 **읽는 방식**을 가리켜야 맞습니다.

| 형식 | 어떻게 트리가 되는가 | 왜 |
| --- | --- | --- |
| JSON | 바이트 스캐너가 원본 위에서 직접 | 파싱 트리를 만들지 않는 것이 전부이기 때문 |
| JSONC | 같은 스캐너, 관대한 쪽으로 | 아래 참조 |
| JSONL | 기본은 표. 형식을 JSON 으로 바꾸면 같은 스캐너가 합성 루트로 감쌉니다 | 아래 참조 |
| XML | 전용 스캐너가 원본 위에서 직접 (`xml.rs`) | 아래 참조 |
| YAML · TOML | JSON으로 변환한 뒤 스캐너에 (`convert.rs`) | 파서가 어차피 값을 메모리에 만들기 때문 |

**YAML과 TOML은 JSON으로 옮깁니다.** 둘 다 JSON이 이미 표현하는 모양의 트리이고, 정작 중요한 부분 — 평면 인덱스, 접기, 가상 스크롤, 경로 검색 — 은 전부 그 모양 위에 서 있습니다. 스캐너를 두 개 더 쓰면 그 모든 걸 두 번 더 구현하면서 독자가 얻는 건 없습니다. 대신 **원본 바이트는 그대로 남아** 원문 보기가 여전히 원래 파일을 보여줍니다. 값을 메모리에 올리는 파서를 쓰므로 64MB 상한이 있습니다 — 설정 파일이 사는 크기와는 자릿수가 다릅니다.

키 순서는 파일에 적힌 순서 그대로입니다(`toml` 은 `preserve_order`, `serde_yaml_ng` 의 매핑은 원래 삽입 순서). 알파벳순으로 재배열된 설정은 원본과 대조하기 어렵습니다. JSON에 없는 값들은 버리지 않고 옮깁니다: 문자열이 아닌 YAML 키는 그 스칼라 텍스트로, TOML 날짜는 적힌 문자열로, `.inf`·`.nan` 은 `null` 이 아니라 문자열로 — 트리에서 낯설게 보이는 것이 정직한 결과입니다.

**XML은 변환하지 않습니다.** JSON으로 옮기면 독자가 신경 쓰는 바로 그 지점들이 무너집니다: 속성이 자식 요소와 구분되지 않고, 같은 이름의 형제 둘은 배열로 접히며(하나일 때와 둘일 때 구조가 달라집니다), 이름이 다른 요소들 사이의 순서가 사라지고, 주석은 없어집니다. 뷰어의 일은 파일에 적힌 것을 보여주는 것이라 XML은 자기 스캐너와 자기 노드 종류(`element`·`attribute`·`text`·`comment`·`cdata`)를 갖습니다. 스캔 이후의 모든 단계는 공유합니다.

XML 쪽에서 내린 판단 몇 가지:

- `<name>John</name>` 처럼 **내용이 텍스트뿐인 요소는 한 줄**로 접습니다(`elementText`). 펼쳐야 "John"이 나오는 트리는 클릭 한 번과 한 줄을 정보 없이 쓰게 만듭니다. 속성이 하나라도 있으면 접지 않습니다 — 속성이 있을 자리가 필요하기 때문입니다.
- **속성은 자식 노드**이고 `@id` 로 표시됩니다. 우리 트리는 맵이 아니라 정렬된 배열이라 이름 중복도 순서도 그대로 살아 있습니다.
- 요소 사이의 **공백만 있는 텍스트는 버립니다.** 들여쓰기는 내용이 아니고, 남기면 형제마다 빈 행이 하나씩 끼어듭니다.
- `<?xml ... ?>` 선언은 버립니다. 파일의 인코딩에 대한 정보이지 문서의 내용이 아니고, 남기면 거의 모든 문서가 루트 요소와 함께 최상위 노드 둘을 갖게 되어 합성 루트가 강제됩니다.
- 잘못 닫힌 태그에도 문서를 보여줍니다. 뷰어가 파일을 여는 이유는 대개 그 파일에 문제가 있어서입니다.

- 경로는 **XPath 모양**입니다: `/catalog/book[2]/@id`. 대괄호 안은 XPath와 같은 의미로 *같은 이름* 요소 중 몇 번째인지이고, 이름이 형제 중 유일하면 붙이지 않습니다. 다만 **경로 검색**에는 이 숫자가 붙지 않습니다 — 검색창에 `[2]` 를 치는 사람은 없고, 숫자가 있으면 `item` 이 모든 item에 걸리지 않게 됩니다.

### JSONC: 관대함은 별도의 형식으로

주석과 후행 쉼표가 있는 JSON 입니다. `.json` 은 그대로 엄격합니다 — 잘못된 파일을 말없이 읽어 주는 뷰어는 독자에게 그 파일이 멀쩡했다고 가르칩니다.

**스캐너는 하나입니다.** 차이가 작아서 — 값과 값 사이에 무엇이 올 수 있는가, 그리고 쉼표가 컨테이너의 마지막 것이어도 되는가 — 두 번째 스캐너를 두면 그건 첫 번째를 복사한 것이 되고, 뒤처지는 건 언제나 복사본입니다. `Dialect` 하나로 갈라집니다.

**주석은 노드가 되지 않습니다.** XML 에서는 주석이 노드인데 여기서는 아닙니다. 모순처럼 보이지만 이유가 다릅니다 — XML 경로는 *같은 이름* 요소의 순번이라 주석이 끼어도 흔들리지 않습니다. JSON 배열 경로는 자식 순번 **그 자체**입니다. 배열 안의 주석이 자식이 되면 `$.items[3]` 이 세상의 다른 모든 JSON 도구와 다른 것을 가리킵니다. 뷰어가 내놓는 경로가 어긋나는 것은 주석을 못 보는 것보다 나쁩니다.

건너뛴다고 잃는 것은 아닙니다. 노드의 텍스트는 문서의 원래 바이트에서 잘라 오므로, 컨테이너를 복사하면 그 안의 주석이 쓰인 그대로 딸려 옵니다.

**막다른 길을 만들지 않습니다.** `tsconfig.json`·편집기 설정처럼 확장자는 `.json` 인데 내용은 JSONC 인 파일이 흔합니다. 이름으로 특례를 두면 "`.json` 은 엄격하다"가 무너지니, 대신 **엄격한 읽기가 멈춘 자리가 JSONC 였다면 지나갔을 자리일 때** 오류 메시지에 전환 안내를 덧붙입니다. 판정은 두 모양뿐입니다 — 주석이 시작되는 자리, 그리고 쉼표를 뒤에 둔 닫는 괄호. 읽기 자체는 한 치도 물러서지 않고, 길만 알려 줍니다.

### CSV·TSV·텍스트: 표는 트리가 아니다

격자를 `행[3].열[7]` 로 펴서 트리에 넣을 수도 있었지만, 그건 표를 읽는 방법으로서 표보다 나쁩니다. 그래서 표는 자기 뷰를 갖습니다.

인덱싱의 거래는 JSON과 같습니다. 바이트를 한 번 훑으며 **각 레코드가 시작하는 위치만** 기록하고, 나머지는 누가 물어보기 전까지 파싱하지 않습니다. 300MB 내보내기 파일이 행당 4바이트를 미리 쓰고, 실제로 칸으로 쪼개지는 건 화면에 있는 백여 행뿐입니다. `split('\n')` 이 아닌 이유는 하나입니다 — 따옴표 안의 개행은 값의 일부이지 행의 끝이 아닙니다.

표로 가는 세 형식도 같은 코드가 읽습니다. 다만 **레코드를 무엇으로 끊고 한 레코드를 어떻게 나누는가**만 다릅니다 (`table::Records`):

| | 레코드 경계 | 칸 나누기 |
| --- | --- | --- |
| CSV · TSV | 개행. 단 **따옴표 안의 개행은 레코드를 잇습니다** (RFC 4180) | 구분자 |
| 텍스트 | 개행. 언제나 | 나누지 않음 — 한 줄이 한 칸 |
| 로그 | 개행. 언제나 | 알아본 배치대로 (아래) |

이 차이를 "구분자가 있냐 없냐"로 적지 않은 이유가 있습니다. 로그에서 따옴표 하나가 다음 스무 줄을 한 레코드로 삼키면 독자는 그것을 설명할 방법이 없습니다. 반대로 CSV 에서 따옴표가 개행을 잇지 못하면 값이 깨집니다. 둘은 같은 바이트를 다르게 읽는 **규칙**이고, 타입 이름이 그것을 말합니다.

덕분에 레코드 인덱스·페이징·검색·복사·취소·4GB 상한과 그리드 화면 전체가 그대로 재사용됩니다. 텍스트를 위해 새로 쓴 것은 스캔의 따옴표 분기와 칸 나누기 한 줄뿐입니다. 미리보기에서 따옴표를 벗기는 처리도 CSV 에만 적용됩니다 — 따옴표로 시작하는 로그 줄은 그 따옴표가 줄의 일부입니다.

#### 로그를 열로 나누기 (`log.rs`)

이 모듈이 지키는 규칙은 절제입니다. **앞에서 확실히 필드인 것만 떼고, 나머지는 메시지 한 열에 통째로 둡니다.** 메시지를 끝까지 쪼개려 들면 형식이 조금만 달라도 값이 엉뚱한 칸에 들어가는데, 잘못 쪼갠 표는 1열 표보다 나쁩니다 — 독자는 무엇이 어디로 갔는지 볼 수 없고, 보던 자리에는 문장의 절반만 남습니다.

확신 순서대로 둘을 알아봅니다.

1. **logfmt** — `level=info msg="시작" port=8080` 처럼 줄 전체가 쌍입니다. 열은 표본에 나온 키의 합집합이고 순서는 첫 등장 순입니다. 어떤 줄에 없는 키는 빈 칸으로 둡니다 — 그 쌍이 적히지 않았다는 뜻이므로 그것이 정직한 표시입니다.
2. **접두 구조형** — `2026-08-30T01:02:03Z INFO [server] 메시지`. **시각은 반드시 필요합니다.** 산문으로 오해할 수 없는 유일한 토큰이기 때문입니다. 수준과 `[...]` 필드는 대부분의 줄이 가질 때만 열이 됩니다 — 몇 줄을 위해 열을 만들면 나머지 전부가 빈 칸이 됩니다.

어느 쪽도 아니면 나누지 않습니다. 문턱은 표본의 70% 로 높게 두었습니다. 날짜 한 줄이 든 회의록이 표가 되면 안 됩니다.

**들여쓴 줄은 표본에서 뺍니다.** 스택 트레이스는 앞 레코드의 연속이지 실패한 로그 줄이 아니고, 분모에 세어 넣으면 진짜 로그가 로그가 아니게 됩니다. 실제로 `sample.log` 가 4/6 = 0.67 로 문턱을 못 넘던 것이 이 때문이었습니다.

**`키=값` 펼치기는 선택입니다.** 기본은 메시지에 두고, 도구 모음에서 켜면 메시지 끝에 붙은 쌍이 각각 열이 됩니다. 이때 메시지는 산문만 남기고 그 쌍들을 내줍니다 — 양쪽에 두면 같은 말을 두 번 하고, 끝의 연속된 쌍이 아닌 곳에서 자르면 문장이 잘립니다. `port=8080 으로 시작함` 처럼 문장 속에 있는 쌍은 자르지 않습니다.

**레코드는 줄이 아닐 수 있습니다.** 스택 트레이스는 자기를 낳은 오류에 속하므로, 접두 구조형에서는 **시각으로 시작하지 않는 줄은 앞 레코드의 연속**입니다. 그래서 색인이 둘입니다 — 줄 시작과 레코드 시작. 둘 다 같은 한 번의 훑기에서 나오고, 그래서 "줄로 보기"가 여전히 표시 전환입니다. 줄 색인은 없어진 적이 없습니다.

모든 줄이 자기 레코드를 시작하면 두 색인이 같은 목록이므로 하나만 둡니다. 207MB 로그에서 색인이 8MB 그대로인 이유입니다.

**레벨 색조는 레벨 칸에만** 넣습니다. 행 전체를 칠하면 얼룩말 줄무늬와 싸우고 표가 데이터보다 시끄러워집니다. ERROR·FATAL·CRITICAL 과 WARN·WARNING 만 색이 붙고 나머지는 본문색입니다. 칸에 이미 레벨 이름이 적혀 있으므로 색은 두 번째 단서이지 유일한 단서가 아닙니다.

**두 전환 모두 표시 모드입니다.** 레코드 인덱스는 어느 쪽이든 같으므로 다시 읽지 않습니다. 1a 에서 `Records` 를 열거형으로 둔 이유가 이것이고, 로그는 그 세 번째 가지입니다.

`split` 은 슬라이스가 아니라 **바이트 범위**를 돌려줍니다. 줄에 없는 필드는 빈 범위로 말할 수 있지만, 빈 문자열은 그 줄의 어디에서 왔는지 말하지 못합니다 — 포인터 차이로 위치를 복원하려다 그 자리에서 프로세스가 죽는 것을 겪고 고친 부분입니다.

확장자가 없거나 어느 형식으로도 판별되지 않는 파일은 **텍스트**입니다. 한때 마크다운이었는데, 그러면 평범한 파일이 렌더링돼 별표가 강조가 되고 우물정자가 제목이 됐습니다. 이름 없는 파일은 로그나 덤프인 경우가 훨씬 많고, 마크다운으로 보고 싶으면 도구 모음에서 바꾸면 됩니다.

**구분자는 내용에서 추측합니다.** 확장자만 믿으면 세미콜론으로 저장하는 유럽 스프레드시트의 `.csv` 가 한 열짜리 표로 보이고, 그건 파일이 안 열린 것처럼 보입니다. 따옴표 밖의 문자만 세므로 값 안의 쉼표가 진짜 구분자를 이기지 못합니다. `.tsv` 는 이름이 이미 구분자를 말하고 있으므로 그대로 믿습니다.

머리글 행과 행 번호 열은 **양방향으로 고정**됩니다. 넓은 표에서 열 이름이나 행 번호가 스크롤되어 사라지면 표는 의미를 잃습니다. 열 너비는 머리글과 첫 페이지에서 추정하고(전체를 재려면 파일 전체를 읽어야 하는데, 이 뷰가 존재하는 이유가 바로 그걸 피하는 것입니다) 경계를 끌어 조절할 수 있습니다. 두 번 누르면 지금 보이는 행들에 맞춰 다시 잽니다.

칸 미리보기도 트리와 같은 규칙으로 **한 줄**이고, 복사는 실제 값을 줍니다 — 따옴표를 벗기고 `""` 를 하나로 되돌립니다. 다른 점은 하나뿐입니다: JSON 미리보기는 JSON 문자열 본문으로 읽혀야 해서 따옴표까지 이스케이프하지만, CSV 칸에는 그런 요구가 없고 따옴표는 산문에 흔해서 전부 이스케이프하면 소음이 됩니다.

검색은 원본 바이트에서 찾은 뒤 이진 탐색으로 레코드를 되짚고, 그 행 하나만 칸으로 쪼개 어느 칸인지 정합니다. 구분자나 따옴표를 걸치는 매치는 어느 칸에도 속하지 않으므로 버립니다. 머리글 행의 매치도 건너뜁니다 — 머리글은 늘 화면에 있어서 이동할 곳이 아닙니다.

#### JSONL: 한 줄이 한 행이다 (`jsonl.rs`)

JSONL 파일과 logfmt 로그는 문장부호만 다른 같은 문서입니다. 한 줄이 한 레코드이고, 레코드는 이름 붙은 필드이며, 열은 그 이름들의 합집합입니다. 그래서 규칙도 `log.rs` 가 이미 정한 것 그대로입니다 — 열은 처음 나온 순서대로, 없는 키는 빈 칸(쓰이지 않은 필드이므로), 표본의 다수가 동의할 때만 표로.

다른 것은 **값이 어디서 끝나는가**인데, 그건 JSON 이 정확히 말해 줍니다. 여기서는 추측하지 않고 **문서 자신의 스캐너**로 각 줄을 읽습니다. 표의 칸과 트리의 노드가 같은 바이트라는 뜻이고, 두 번째 파서가 첫 번째와 다른 답을 내는 일이 없습니다.

비용은 실측이 답합니다. 색인은 개행만 세므로 로그와 같고(438MB·200만 행에 0.36초, 8MB), 줄을 JSON 으로 읽는 일은 **화면에 있는 행에서만** 일어납니다 — 100행에 0.1ms. 파일이 커져도 그 값은 그대로입니다.

문자열은 따옴표를 벗깁니다. 표는 값을 보여주는 자리고, 모든 행에서 `"error"` 의 따옴표를 넘겨 읽게 하는 것은 눈에 대한 세금입니다. 나머지는 쓰인 그대로라 숫자는 숫자로, `null` 은 `null` 로 남고, 중첩된 값은 자기 JSON 텍스트로 한 칸에 들어갑니다 — 더 쪼개면 파일이 약속하지 않은 모양을 지어내는 것입니다.

객체가 아닌 줄은 첫 칸에 통째로 둡니다. 잘려 쓰인 마지막 줄이 실제로 있는 경우이고, 사라진 행이 잘못된 자리에 있는 행보다 나쁩니다. 한 열 보기로 접으면 원래 줄 그대로 보입니다.

### SQLite: 바이트가 아닌 첫 형식

여기까지의 여덟 형식은 모두 한 줄기 바이트였습니다. mmap, 인코딩 판별, 바이트 검색, 원문 보기가 전부 그 전제 위에 서 있습니다. 데이터베이스는 그렇지 않습니다 — 질의로 읽습니다. 그래서 갈라놓은 것들:

- **판별은 매직 바이트가 합니다.** `.db` 는 열 가지 형식의 이름이고, 확장자 없는 데이터베이스도 앞 16바이트가 자기를 밝힙니다. 이름은 마지막 단서입니다.
- **인코딩 파이프라인을 지나지 않습니다**(`encoding::verbatim`). 어떤 인코딩으로도 텍스트가 아닌 바이트에 판별기를 돌리면 확신에 찬 오답만 나옵니다.
- **형식 전환 목록에 없습니다.** 그 목록은 한 줄기 바이트를 달리 읽는 방법들이고, 데이터베이스에는 달리 읽을 것이 없습니다. 양방향 모두 거절합니다(`notInterchangeable`).
- **주소로는 열 수 없습니다**(`needsFile`). 내려받은 버퍼에는 질의할 파일이 없습니다. 임시 파일로 쓰면 동작하겠지만, 독자가 두겠다고 하지 않은 자리에 데이터베이스 사본이 남습니다.

**여는 방식은 곁의 파일이 정합니다.** `immutable=1` 은 잠금을 건너뛰어 남이 쥐고 있는 파일도 열지만 WAL 을 무시합니다 — 최근 기록을 조용히 빠뜨리느니 공유 잠금을 잡는 편이 낫습니다. `-wal`/`-journal` 이 있으면 뺍니다.

**컬렉션 선택은 형식 중립입니다.** `CollectionPicker` 는 이름 목록과 부차 표시(뷰)만 압니다. 한 파일에 여러 시트가 든 형식이 오면 같은 컴포넌트를 씁니다.

#### 그리드는 하나다

CSV 의 행은 자기 바이트의 구간이고 데이터베이스의 행은 질의가 돌려준 것입니다. 그런데 읽는 사람이 그걸로 하는 일 — 창을 굴리고, 칸을 고르고, 하나를 복사하고, 무언가를 찾고 — 은 똑같습니다. 그래서 차이를 **Rust 경계에서 끝냅니다.**

`Grid` 트레이트 하나에 `grid_rows`·`grid_cell_text`·`grid_row_text`·`grid_search` 네 커맨드가 걸리고, 프런트의 `DataGrid` 는 자기가 무엇을 그리는지 모릅니다. 호스트가 주는 것은 호스트만 아는 것 — 행·열 수, 열 이름, 칸 색조 — 뿐입니다.

트레이트는 좁습니다. 색인(`table_open`)과 모드 전환은 표에 남습니다. 바이트 뭉치만 답할 수 있는 질문이고, 트레이트에 넣으면 구현체마다 거절할 메서드가 하나씩 늘어납니다. 검색은 남기지 않았습니다 — "이 텍스트가 든 칸을 찾아라"는 그리드에 대한 질문이고, 둘이 서로 다른 수단으로 같은 답을 냅니다.

#### 체크포인트: 300만 번째 행

SQLite 는 rowid 로는 즉시 찾아가지만 "300만 번째 행"이라는 개념이 없습니다. 색인이 없으면 `OFFSET 2999940` 이 앞의 300만 행을 전부 밟습니다. 그래서 컬렉션을 고를 때 rowid 만 한 번 훑으며 **1,024행마다 하나씩** 적어 둡니다. 조회는 탐색 한 번과 1,023걸음 이내가 되고, 300만 행에 22KB 를 씁니다. 실측은 [검증과 성능](verification.md)에 있습니다 — 271ms 대 0.15ms.

보폭이 고정이라 이진 탐색조차 필요 없습니다. 행 번호를 1,024로 나누면 그것이 색인입니다.

훑기에는 상한이 있습니다(500만 행). 상한에 걸리면 상태줄이 그렇게 말합니다 — 기다리게 두는 것보다 낫습니다.

rowid 가 없는 것(뷰, WITHOUT ROWID 테이블)은 적어 둘 것이 없어 `LIMIT`/`OFFSET` 을 탑니다. 앞쪽은 똑같이 빠르고 뒤로 갈수록 느려집니다.

**긴 일은 자기 연결에서 합니다.** 훑기와 검색은 각자 연결을 엽니다. 공유 연결의 락을 그 시간만큼 쥐면 화면이 검색을 기다리게 되는데, 읽는 사람이 언제나 할 수 있어야 하는 일이 바로 그 화면 보기입니다.

#### 다섯 저장 클래스

NULL 은 빈 문자열이 아닙니다. 같게 그리면 거짓말이라 흐린 기울임 `NULL` 로 따로 그립니다. BLOB 은 바이트가 만들 뭉개진 글자 대신 16진으로, 잘린 자리에는 크기를 붙여서 — 읽을 수 없는 값에 대해 쓸모 있는 사실은 크기입니다. 실수는 `1.0` 이 정수로 보이지 않게 씁니다.

CSV 쪽 `null` 플래그는 언제나 거짓입니다. 없는 칸과 빈 칸이 바이트로 같은데 차이를 지어내면 데이터를 지어내는 것입니다.

검색도 이 구분을 따릅니다. NULL 은 어떤 글자에도 걸리지 않고, BLOB 은 검색되지 않습니다 — 화면의 16진은 이 앱의 표기이지 파일이 말하는 바가 아니라서, 거기에 맞추면 데이터에 없는 것을 찾아 줍니다.

### xlsx: 시트의 좌표는 시트의 것이다

바이트가 아닌 두 번째 형식인데, SQLite 와는 다른 이유로 그렇습니다. 질의하는 것이 아니라 **YAML·TOML 처럼 변환**됩니다 — 라이브러리가 파일을 메모리의 값으로 바꾸므로 열 수 있는 크기에 상한(64MB)이 있습니다. xlsx 는 특히 부풀어 오릅니다: 공유 문자열은 디스크에서 색인 하나지만 메모리에서는 문자열 하나씩입니다.

SQLite 와 공유하는 것은 **모양**입니다 — 한 파일에 여러 컬렉션, 그중 하나가 화면에. 그래서 같은 `Grid` 로 답하고 같은 선택기로 고릅니다. `DocView::Collection` 이라는 이름이 여기서 값을 합니다.

**좌표는 시트의 것입니다.** 열 이름은 `A`·`B`·`AA`, 1행은 1행입니다. 뷰어로 스프레드시트를 여는 사람은 대개 원본과 대조하는 중이고, "15행 D열"이 양쪽에서 같은 곳을 가리켜야 합니다. 첫 행을 머리글로 올리지 않는 이유도 그것입니다 — 모든 행 번호가 하나씩 밀립니다.

여기에 함정이 하나 있습니다. calamine 의 범위는 **쓰인 칸에서 시작**하므로, C4 에서 시작하는 시트는 첫 칸이 C4 인 행렬을 돌려줍니다. 그걸 A1 부터로 읽으면 모든 값이 두 열 세 행씩 옮겨집니다. 시작점을 기억했다가 조회할 때 빼는 쪽을 택했습니다 — 빈 자리를 메모리에 채우지 않고도 좌표가 맞습니다. 수식 범위는 자기만의 시작점을 가지므로(첫 수식이 첫 값인 경우는 드뭅니다) 따로 기억합니다. 픽스처의 둘째 시트가 C4 에서 시작하는 것은 이걸 잡기 위해서입니다.

**날짜는 ISO 8601 입니다.** 셀의 서식을 흉내내려면 Excel 의 숫자 서식 언어를 다시 구현해야 하는데, 미묘하게 틀리기 쉬운 넓은 표면이고 **미묘하게 틀린 날짜가 대놓고 다른 날짜보다 나쁩니다.** `30-Aug` 같은 서식은 연도까지 잃습니다. 일련번호가 1 미만이면 날짜 없는 시각이므로 시각만 씁니다 — 그때 찍히는 1899년은 표현 방식의 흔적이지 누가 쓴 것이 아닙니다.

**수식은 요청할 때만 읽습니다.** 기본은 Excel 이 마지막으로 계산해 둔 값이고, 토글을 켜면 그 시트의 수식을 한 번 읽어 보여줍니다. 칸마다 표를 붙이는 대신 토글을 둔 것은, 재무 시트라면 거의 모든 칸에 표가 붙어 신호가 죽기 때문입니다.

### Parquet: 형식이 이미 이 설계를 하고 있었다

이 뷰어가 형식마다 애써 만들어 온 것 — 통째로 올리지 않고, 색인을 두고, 닿는 부분만 읽는 것 — 을 Parquet 은 파일 구조로 이미 갖고 있습니다. 행 그룹 단위로 쓰이고 색인이 끝에 붙어 있어서, 여는 일은 푸터를 읽는 일입니다. 52MB·행 그룹 8개에 **0.19ms**, 311MB·행 그룹 48개에 **0.61ms** — 자라는 것은 파일 크기가 아니라 **행 그룹 수**입니다. 파일이 여섯 배가 되어도 푸터는 여섯 배가 되지 않습니다.

그래서 여기엔 전체 상한이 없습니다. xlsx 는 통째로 변환하니 있고, 데이터베이스는 질의하니 없고, 이건 두 번째 이유로 없습니다.

**arrow 를 쓰지 않습니다.** arrow 리더는 컬럼 배치를 만드는데, 그건 파일 위에서 계산할 때의 모양이지 백 행을 보여줄 때의 모양이 아닙니다. 그리고 그걸 얻자고 의존 크레이트가 두 배가 됩니다. arrow 없는 `SerializedFileReader` 는 행 그룹 하나를 행 단위로 주는데, 그게 정확히 그리드가 원하는 것입니다.

**값을 치르는 자리는 하나뿐입니다.** 처음 닿는 행 그룹을 통째로 푸는 순간(25만 행에 150ms). 행 그룹은 페이지가 함께 압축된 단위라 절반만 풀 수 없고, 그래서 **그 크기에만 상한**을 둡니다 — 400만 행, 실측에서 2.5초쯤에 해당하는 지점입니다. 푼 그룹은 두 개까지 들고 있습니다.

**타입 표기는 새로 정하지 않았습니다.** 타임스탬프 ISO 8601, NULL 플래그, 바이너리 hex(잘린 자리에 크기), 중첩은 한 칸에 JSON 모양 — 전부 SQLite 와 xlsx 가 이미 정한 것입니다. 크레이트의 `Display` 는 숫자와 날짜만 우리와 같고 문자열엔 따옴표를, 타임스탬프엔 `2026-08-29 10:40:00.000 +00:00` 을, 바이너리엔 십진수 목록을 줍니다. 그래서 그 셋은 우리가 씁니다.

`hex_cell` 이 `grid.rs` 로 올라간 것도 이때입니다. 데이터베이스의 BLOB 과 스프레드시트·Parquet 의 바이너리 열은 읽는 사람에게 같은 것이고, 두 가지로 그리면 설명할 수 없는 차이가 됩니다.

**스키마를 보여줍니다.** 격자만으로는 어떤 `INT64` 가 타임스탬프인지 알 수 없는데, 그건 독자가 가장 자주 확인하는 사실입니다. SQLite 의 DDL 버튼이 이미 그 자리였습니다 — 한 파일에 하나뿐인 컬렉션이라 선택기는 스스로 숨고(항목이 둘 미만이면 그립니다), 화면에는 스키마 버튼과 격자만 남습니다.

### 정규식: 앵커가 뜻을 가지려면

검색창의 `.*` 를 켜면 질의를 정규식으로 읽습니다. **범위(전체·키·값·경로)와는 별개의 축**입니다 — 범위는 노드의 어디를 볼지, 이쪽은 찾는 것을 어떻게 읽을지 정합니다. 기본값이 리터럴이라 켜지 않는 사람에게는 아무것도 달라지지 않습니다.

**질의 모양으로 자동 판별하지 않습니다.** `$.items` 는 오늘도 경로 부분 일치로 잘 동작합니다. 모양을 보고 몰래 다른 엔진으로 넘기면 어제 되던 검색이 오늘 다른 답을 내고, 읽는 사람에게는 이유를 볼 방법이 없습니다.

**매치 단위는 키 하나, 값 하나입니다.** 바이트 스트림 전체에 정규식을 걸지 않습니다. 이건 청크 스캔의 겹침 창(고정 길이 패턴 전제)을 피하려는 우회가 아니라, **앵커가 뜻을 갖는 유일한 읽기**이기 때문입니다. `^`·`$` 는 바이트 스트림에서 파일의 아무 개행에나 걸리는데, JSON 문서에서 그건 아무것도 뜻하지 않습니다. `^\d+$` 같은 가장 흔한 패턴이 엉뚱한 답을 냅니다.

기계는 새로 만들지 않았습니다. 경로 검색이 이미 바이트 스캔이 아니라 노드 walk 였고, 키·값 정규식은 그 walk 를 다른 필드에 대해 하는 것입니다. 실측도 같은 자릿수입니다 — 3,840만 노드 파일에서 리터럴 바이트 스캔 1.16초, 정규식 노드 walk 1.73초, 경로 walk 2.22초.

**패턴은 문자를 읽고, 리터럴은 바이트를 읽습니다.** 그래서 정규식은 값의 문자(이스케이프가 풀리고 따옴표가 벗겨진 것)를 보고, 리터럴은 파일의 바이트를 봅니다. `\n` 을 찾으면 전자는 진짜 개행을, 후자는 역슬래시와 n 두 글자를 찾습니다 — 둘 다 자기 질문에 대해 맞습니다.

**격자도 같은 규칙입니다.** 매치 단위는 칸이고, 보는 것은 칸의 값입니다 — CSV 라면 따옴표가 벗겨지고 `""` 가 한 글자로 합쳐진 그 텍스트, 곧 칸을 복사했을 때 나오는 것입니다. `Grid::search` 가 해석 모드를 받고, 네 구현체(표·SQLite·xlsx·Parquet)가 같은 `Matcher` 로 묻습니다.

바이트 격자에서는 이것이 바이트 스캔이 아니라 레코드 walk 가 된다는 뜻이라, 비용을 재고 결정했습니다. 298MB·400만 행 × 12열(4,800만 칸)에서 **1.48초** — 리터럴 스캔 0.05초의 서른 배지만 트리 정규식 1.73초와 같은 자릿수이고, 앵커를 붙여도 1.47초로 달라지지 않습니다.

그래서 **프리필터를 두지 않았습니다.** 레코드로 먼저 거르는 2단계를 고려했지만, 그러려면 정규식이 원시 바이트를 봐야 하고 그러면 칸의 값(`""` → `"`)과 어긋납니다. 1.5초는 취소 가능한 백그라운드 작업으로 충분히 감당할 값이고, 대신 **한 격자 안에서 리터럴과 정규식이 각자 자기 텍스트를 일관되게 봅니다.**

칸마다 `String` 을 만들면 4,800만 번의 할당이 루프에서 가장 비싼 일이 됩니다. 버퍼 하나를 비우고 다시 채웁니다.

컴파일에 실패한 패턴은 크레이트의 메시지 그대로 돌려줍니다. 어느 자리가 왜 틀렸는지는 그쪽이 이 앱보다 잘 압니다.

### 트리 읽기: 색이 아니라 선

계보를 알려주는 건 **선**입니다. 색은 같은 깊이의 다른 형제 블록에 같은 값을 주므로 "몇 층인가"만 답할 뿐 "어느 부모에 속하는가"를 답하지 못하고, 키에 색을 입히면 값 타입 색과 경쟁합니다. 그래서 구조는 세로 가이드선이 담당합니다.

그 위에 **깊이별 색조를 보조 단서로** 얹었습니다 (`--guide-1` … `--guide-9`, 9단계마다 순환). 가이드는 왼쪽 여백의 1px 선이라 값 색과 겹칠 일이 없고, 층수를 세지 않고도 눈으로 가늠하게 해줍니다.

색은 눈대중으로 고르지 않았습니다. 색상환을 9등분(40°)하고 레벨 k에 `((k-1) × 4 mod 9)` 번째 칸을 배정하면 **인접한 모든 쌍이 정확히 160° 떨어집니다** — 9에서 1로 되돌아가는 순환 지점까지 포함해서요. 9주기 순환에서 얻을 수 있는 최대 간격입니다. 여기에 명도를 홀짝으로 번갈아 줘서 이웃한 레벨은 색상과 밝기 두 가지로 갈라지고, 색각 이상에서도 구분됩니다.

선택한 블록의 가이드를 강조할 때는 **그 레벨의 색조를 유지한 채** 본문 색 쪽으로 밀어 넣습니다 (`color-mix(in oklab, var(--guide-color) 78%, var(--text))`). 라이트에서는 어두워지고 다크에서는 밝아지는데, 한 가지 강조색으로 통일해 버리면 독자가 따라가던 단서 자체를 지우게 되기 때문입니다.

행을 선택하면 그 행의 **직속 부모 가이드가 블록 범위만큼 강조**됩니다. 선행순서 나열에서 블록은 연속 구간이므로, 로드된 창에서 선택 지점 위아래로 깊이가 낮아질 때까지 훑으면 형제 그룹의 정확한 범위가 나옵니다 — 백엔드에서 추가 데이터를 받을 필요가 없습니다.

행 미리보기는 항상 **한 줄**입니다. 트리는 행을 고정 높이로 그리고 인덱스로 위치를 잡으므로, 개행이 든 값은 아래 행들 위에 겹쳐 그려집니다(26px 행에 68px 텍스트). 그래서 제어 문자로 디코드되는 이스케이프는 이스케이프 형태로 남깁니다 — `"a\nb"` 는 `a\nb` 로 보입니다. 렌더링 가능하면서 파일에 실제로 적힌 그대로입니다. 스캐너가 관대해서 문자열 안에 진짜 제어 문자가 들어올 수도 있으므로 그것도 같이 처리하고, CSS가 줄바꿈으로 취급하는 U+2028/U+2029 도 포함합니다. 미리보기는 **JSON 문자열 본문 형태**입니다 — 백슬래시와 따옴표도 이스케이프합니다. 안 그러면 `"a\nb"`(개행)와 `"a\\nb"`(백슬래시+n)가 화면에 똑같이 보여 서로 다른 두 값이 구분되지 않고, 어디까지가 이스케이프인지도 알 수 없습니다.

그 덕에 프론트엔드는 백슬래시를 만나면 무조건 이스케이프의 시작으로 읽을 수 있고, 이스케이프 구간에만 별도 색과 옅은 배경 칩을 입힙니다. 색만으로는 부족합니다 — 글자가 앞뒤 단어에 붙어 보이는 걸 실제로 끊어주는 건 칩의 경계입니다.

**복사는 반대 일**입니다. 미리보기는 한 줄이어야 하지만 클립보드는 값 자체를 원하므로, 문자열은 따옴표를 벗기고 이스케이프를 실제 문자로 되돌려 줍니다 — 행에는 `a\nb` 로 보여도 붙여넣으면 진짜 두 줄입니다. 오브젝트·배열은 원본 JSON을 그대로 돌려줍니다. 그쪽은 소스가 곧 값이고, 다른 곳에 붙여넣을 수 있어야 하기 때문입니다.

트리의 행은 뷰포트에 맞춰 자르지 않고 **내용 길이만큼** 늘어납니다. 긴 값은 말줄임표로 끝나는 대신 가로 스크롤로 끝까지 볼 수 있습니다(행 미리보기는 노드당 500자까지 전달됩니다).

컨테이너 행의 `{ 3 }` · `[ 3 ]` · `< 3 >` 는 **눌러서 접고 펼칠 수 있습니다.** 접힌 내용을 대신하는 표기라서 그것을 눌러 펼치는 것이 먼저 시도하게 되는 동작이고, 왼쪽 끝의 삼각형은 1.1em짜리 과녁입니다. 같은 트리 엔진을 쓰는 YAML·TOML·XML도 똑같이 동작합니다. 키보드 담당은 여전히 삼각형이라 표기 쪽은 탭 순서에 끼어들지 않습니다.

옆의 **키/값 표**는 트리가 답하지 않는 질문을 맡습니다. 트리는 "지금 어디인가"를, 표는 "여기에 무엇이 있는가"를 보여줍니다. 컨테이너를 선택하면 그 하위 항목을, 스칼라를 선택하면 그 항목이 놓인 **레벨**(부모의 하위 항목)을 보여줍니다 — 어느 쪽인지는 Rust의 `TreeIndex::table_target` 이 정하므로 프론트엔드는 부모를 알 필요가 없습니다. 표 안의 오브젝트·배열은 값을 한 줄로 적을 수 없으니 `{ … }` / `[ … ]` 로 두고, 누르면 트리에서 그 노드를 클릭한 것과 같이 동작합니다.

긴 값은 칸에서 잘리는데, **눌러서 그 자리에서 펼칩니다.** 아무것도 펼치지 않은 화면은 그대로이고 펼친 행만 자랍니다. 펼친 값은 `tree_node_text` 로 가져옵니다 — 행이 들고 있는 것은 500자까지의 이스케이프된 미리보기라 `a\nb` 가 글자 그대로지만, 펼치면 진짜 두 줄입니다. 복사가 이미 하던 구분과 같습니다. 8MB 까지 오는 값을 통째로 그리지는 않고 2만 자에서 끊습니다.

펼친 값과 그 행은 왼쪽 레일과 같은 색조로 묶고, 값 칸 맨 위에 키를 되풀이합니다. 값이 길면 정작 그 행은 위로 스크롤돼 사라지기 때문입니다. 레일은 배경 그라디언트입니다. `border-collapse` 표의 셀에는 그림자가 그려지지 않고, 테두리는 셀에서 2px 를 가져가는데 행은 지금 크기 그대로 측정된 것이라 상자를 건드리면 안 됩니다.

**어느 행이 잘렸는지는 재서 압니다**(`tree/measure.ts`). 셀마다 `scrollWidth > clientWidth` 를 묻는 방법은 한 번에 레이아웃을 강제해서, 이 표의 마크업으로 100행 0.8ms · 2000행 22ms · 10000행 105ms 가 나옵니다. 열 구분선은 드래그하는 매 프레임 다시 확인해야 하는데 예산은 16ms 입니다. 그래서 문자열을 같은 폰트로 canvas 에 재고 행마다 캐시합니다. 드래그는 숫자만 비교해 2000행 0.1ms, 10000행 0.5ms 입니다.

재는 값이 그리는 값과 같아야 해서 세 가지를 맞췄습니다. 이스케이프 칩은 `0 0.1em` 패딩을 가지므로 세그먼트마다 `0.2em` 을 더합니다. 줄 끝 공백은 CSS 가 넘침으로 치지 않으므로 다듬습니다. 그리고 브라우저는 정수인 `scrollWidth` 와 `clientWidth` 를 비교하니 1px 미만 초과는 말줄임을 만들지 않아 0.5px 를 봐줍니다. 셋을 다 넣고 실제 레이아웃과 대조하면 이스케이프·CJK·이모지·아랍어·ASCII 4000행 × 열 너비 9종 = 36,000회 비교에서 불일치가 없습니다(경계 8px 이내 1,741행 포함). 하나라도 빼면 각각 32건, 26건씩 틀립니다.

파고들면 **되돌아올 길**이 필요합니다. 깊은 문서에서 세 단계를 따라 들어가면 읽던 자리로 돌아갈 방법이 없어지기 때문입니다. 그래서 선택이 닿은 노드는 전부 기록되고(`NodeHistory`), 표 머리의 앞/뒤 버튼과 **마우스 옆 버튼**이 그 목록을 걷습니다. 의미는 브라우저와 같습니다 — 중간에서 새 곳으로 가면 앞쪽은 버립니다.

기록은 트리 뷰의 이펙트 **한 곳**에서만 합니다. 트리 클릭이든 표에서 파고들기든 검색 결과 이동이든 결국 선택이 움직이므로, 각 자리에서 따로 적으면 언젠가 한쪽이 빠집니다. `visit` 이 지금 있는 노드를 무시하는 것이 뒤로 가기가 히스토리를 다시 늘리지 않게 하는 장치입니다. 마우스 옆 버튼은 `mousedown` 에서 기본 동작을 막습니다 — 놔두면 웹뷰가 그것을 페이지 이동으로 쓰는데, 단일 페이지 앱에서 그것은 문서를 통째로 내리는 일입니다.

표는 **창으로 떼어낼 수도** 있습니다. 두 곳을 나란히 놓고 비교하려면 그 방법뿐이라, 떼어낸 창은 열릴 때의 노드에 고정됩니다 — 트리에서 다른 것을 선택해도 따라 움직이지 않습니다. 창들은 하나의 `AppState` 를 공유하므로 문서가 복사되지는 않습니다. 떼어낸 창은 같은 페이지를 `?panel=…` 로 열고 프론트엔드가 URL을 보고 표만 마운트합니다. 커맨드가 아니라 URL로 가르는 이유는 그 결정이 **동기적**이어야 하기 때문입니다. 첫 페인트 전에 자기가 무엇인지 알아야 탭 줄이 한 번 번쩍이지 않습니다.

떼어내기 커맨드가 `async` 인 것은 장식이 아닙니다. 동기 커맨드는 이벤트 루프를 도는 스레드에서 실행되고, 거기서 창을 만들면 그 일을 처리해야 할 루프를 자기가 막고 선 채로 영원히 기다립니다. 창틀은 OS가 그려 주니 창은 떠 있지만 웹뷰가 끝내 붙지 않아 내용이 비고, 늘린 영역은 칠해지지 않은 채 검게 남고, 자기 닫기 버튼에도 답하지 않습니다.

패널 너비와 키/값 열의 경계는 모두 끌어서 조절합니다(화살표 키로도 되며 두 번 누르면 기본값). 창을 줄여도 트리 쪽 폭은 확보됩니다. 두 손잡이는 같은 `Splitter` 컴포넌트인데, 측정 방식(패널은 오른쪽 끝에서의 픽셀, 열은 왼쪽에서의 비율)만 콜백으로 주입받습니다.

열 경계는 퍼센트가 아니라 **픽셀 하나**로 계산합니다. 표는 스크롤 영역의 콘텐츠 박스를 채우고 구분선은 패널을 기준으로 놓이는데, 세로 스크롤바가 생기면 그 둘의 폭이 달라져 선이 실제 열 경계에서 어긋나기 때문입니다. 표의 우클릭 메뉴는 트리의 것과 **같은 코드**(`tree/actions.ts`)에서 나옵니다 — 두 벌로 두면 언젠가 한쪽이 엉뚱한 것을 복사하게 됩니다. 본문 행은 얼룩말 줄무늬로 구분하고 행 경계선은 두지 않았습니다. 둘 다 넣으면 표가 데이터보다 시끄러워집니다.

경로는 두 경로로 제공합니다. 마우스는 키 호버 팝오버, 키보드는 상태 표시줄의 선택 행 경로 — 호버 전용 정보를 만들지 않기 위해서입니다.

팝오버는 키 **위쪽**에 뜹니다. 아래는 다음에 눈이 갈 행들이 있는 자리라서입니다 (창 상단에 여유가 없으면 아래로 뒤집습니다). 배경은 페이지와 뚜렷이 다른 전용 토큰(`--popover-bg`)을 쓰는데, 라이트에서 흰 패널을 흰 페이지 위에 띄우면 보이지 않고 다크에서도 그냥 또 하나의 패널로 읽히기 때문입니다. 페이지 대비는 라이트 14.6:1, 다크 3.5:1 입니다.

### gzip

`.gz` 는 확장자가 아니라 **매직 바이트**(`1f 8b`)로 알아봅니다. 이름은 형식을 정하는 데만 쓰입니다 — `report.json.gz` 는 JSON 이고, 그 사실은 안쪽 이름만이 말합니다. 맨 `.gz` 면 안쪽 이름이 없으니 내용으로 판별합니다.

해제는 **다른 무엇보다 먼저** 일어납니다. 압축된 파일은 자기 인코딩도 자기 형식도 말하지 못하기 때문입니다.

**상한은 푼 결과에 겁니다(512MB), 파일 크기가 아니라.** 이것은 정확성 이전에 안전 문제입니다 — gzip 은 1000:1 압축이 가능해서, 1MB 짜리 `.gz` 가 수 GB 를 요구할 수 있습니다. 파일 크기로 걸면 그것을 막지 못하고, 막을 수 있는 유일한 순간은 내용이 나오는 도중입니다. 그래서 스트리밍으로 풀되 상한보다 한 바이트만 더 읽어 보고 넘으면 그 자리에서 멈춥니다.

푼 결과는 힙에 올라가므로 그 문서는 mmap 의 이점을 잃습니다. 인코딩 변환이 이미 같은 거래를 하고 있고(256MB 상한), 상한이 그것을 유한하게 만듭니다. 임시 파일로 풀어 mmap 하는 방법도 있지만 디스크에 흔적을 남기므로 택하지 않았습니다.

원문 보기는 **풀린 내용**을 보여줍니다. 압축된 바이트를 보여주는 것은 아무에게도 쓸모가 없습니다.

zstd 와 bzip2 는 아직 없습니다. 요구가 생기면 같은 자리에 얹으면 됩니다.

### 인코딩

스캐너도, 레코드 인덱스도, 노드를 원본에 되돌리는 바이트 오프셋도 전부 UTF-8을 전제합니다. 좋은 전제이지만 파일이 늘 그렇지는 않습니다 — 한국어 Windows의 Excel은 CSV를 기본으로 **CP949**로 쓰고, "유니코드 텍스트"로 내보내면 **UTF-16**입니다. 그대로 UTF-8로 읽으면 구조는 멀쩡한데 글자가 전부 깨집니다.

그래서 UTF-8이 아닌 문서는 **열 때 한 번 변환**해서 그 결과를 문서로 삼습니다(`encoding.rs`). 판별 순서는 확신이 강한 것부터입니다:

1. **BOM** — 추측이 아니라 선언입니다. UTF-8·UTF-16 LE/BE.
2. **UTF-8로 유효한가** — 유효한 UTF-8이 우연히 다른 인코딩으로도 말이 되는 경우는 거의 없습니다. 이 경우 mmap을 **그대로 통과**시킵니다. 흔한 경우가 공짜여야 500MB JSON이 복사를 치르지 않습니다.
3. **`chardetng` 추측** — 앞의 1MB를 바이트 통계로 판별합니다. Firefox가 쓰는 것과 같은 판별기입니다.

**추측은 틀릴 수 있습니다.** 짧은 파일은 여러 인코딩에서 동시에 유효할 수 있어서, 결과를 도구 모음에 **표시하고 직접 바꿀 수 있게** 했습니다. 추측으로 정해진 경우에만 선택 상자에 테두리 강조가 붙습니다 — BOM·유효한 UTF-8·직접 고른 값은 다 확정된 사실이라 강조할 것이 없습니다. 해석되지 않는 바이트가 있었으면 경고 아이콘과 함께 이유를 붙입니다.

인코딩을 바꾸면 트리·표 인덱스를 전부 버립니다. 바이트 오프셋은 인코딩이 바뀌면 살아남지 못합니다. 원본 바이트는 따로 붙들고 있어서 디스크를 다시 읽지는 않습니다.

`chardetng`은 웹 콘텐츠에 맞춰 조율된 판별기라 ISO-2022-JP는 **막아 두었습니다.** 브라우저가 같은 이유로 막습니다 — 무해한 바이트를 마크업으로 바꿀 수 있는데, 이 문서는 렌더링될 수 있습니다.

변환은 문서를 통째로 메모리에 올리므로 256MB 상한이 있습니다(CP949는 UTF-8로 가면서 한글 한 자당 2→3바이트로 자랍니다). 넘으면 변환하지 않고 도구 모음에 이유를 적습니다 — 조용히 깨진 글자를 보여주는 것보다 낫습니다.

BOM 자체는 모든 형식에서 벗겨냅니다. Windows 편집기가 묻지 않고 붙이는 데다, YAML은 BOM으로 시작하는 문서를 아예 거부합니다.

### 명령줄, 그리고 이미 열려 있는 창

```bash
dviewer report.md                      # 위치 인자
dviewer --open="C:/데이터/큰파일.json"
dviewer --open-url=https://example.com/data.json
dviewer --new --open=a.csv             # 탭이 아니라 새 창으로
```

두 번째 `dviewer` 는 **창을 그리지 않습니다.** 인자를 이미 돌고 있는 프로세스에 넘기고 종료합니다(`tauri-plugin-single-instance`). 그래서 파일 연결이나 셸에서 파일을 열면 창이 계속 늘어나지 않고 **현재 창에 탭으로** 붙습니다. `--new` 를 주면 그때만 창을 하나 더 만듭니다.

그 결과 인자 파싱은 **창이 없는 곳에서 벌어집니다.** 두 번째 프로세스는 이미 없고, 첫 번째 프로세스가 남의 인자를 해석합니다. 그래서 `cli.rs` 의 파서는 창에 의존하지 않는 순수 함수이고 테스트가 붙어 있습니다 — 여기서 실수하면 셸에서 파일을 열어 보기 전까지 아무도 모릅니다.

모르는 플래그는 거부하지 않고 넘깁니다. Windows의 GUI 프로세스는 불평을 찍을 곳이 없어서, 실패시키면 그냥 창이 안 뜨는 것으로 보입니다.

창이 여럿이어도 **백엔드 상태는 하나**입니다. 인덱스는 Rust에 있고 화면에 보이는 행만 오가므로, 한 창에서 연 문서가 다른 창에 비용을 지우지 않습니다. 이벤트는 모든 창에 방송되지만 각 프런트엔드가 문서 id로 걸러 자기 것이 아니면 무시합니다.

새 창이 만들어질 때 열 것을 어떻게 아는가 — 창이 생기기 전에 요청이 도착하므로, `AppState` 에 창 이름별로 대기시켜 두고 프런트엔드가 뜨자마자 가져갑니다(`startup_request`). 가져가면 지워지므로 새로고침해도 같은 파일이 두 번 열리지 않습니다.

`capabilities/default.json` 의 창 목록에 `doc-*` 을 넣어 두었습니다. 그게 없으면 `--new` 로 만든 창은 권한이 하나도 없습니다.

창 크기·위치·최대화 상태는 `tauri-plugin-window-state` 가 종료할 때 저장하고 다음 실행에 복원합니다.

### 새 탭은 시작 화면이다

`+` 와 `Ctrl T` 는 파일 선택 창이 아니라 **시작 화면이 담긴 빈 탭**을 엽니다. 들어오는 길이 넷이기 때문입니다 — 파일, 주소, 붙여넣기, 최근 목록. 파일 선택만 띄우면 나머지 셋은 탭이 하나도 없을 때만 닿을 수 있습니다.

빈 탭에서 무언가를 열면 **그 탭이 채워집니다.** 옆에 새 탭이 생기지 않습니다 — 독자가 출발한 자리가 문서가 도착할 자리입니다. 빈 탭은 하나만 둡니다. 두 번째 빈 탭은 첫 번째와 생김새도 동작도 같아서 이미 있는 것을 올려 줍니다.

### 다국어: 문장은 한 곳에서만 만든다

한국어 · English · 日本語 · 简体中文 네 가지입니다. 기본은 시스템 로케일을 따르고 설정에서 바꿀 수 있으며, **바꾸면 새로고침 없이 화면 전체가 즉시 바뀝니다** — 이미 표시된 오류 메시지까지.

그게 가능한 이유는 **Rust가 문장을 만들지 않기 때문**입니다. 백엔드는 코드와 인자만 보냅니다:

```json
{"code":"tooLarge","params":{"subject":"markdown","megabytes":20,"limitMb":16}}
```

프런트엔드가 이걸 문장으로 만듭니다. `subject` 와 `reason` 은 그 자체가 코드라서 문장에 끼워 넣기 전에 먼저 번역됩니다. 그래서 번역이 Rust와 TS 두 곳으로 갈라지지 않고, 표현 계층이 백엔드에 남지 않습니다. 같은 이유로 CSV 구분자도 `"쉼표"` 가 아니라 `"comma"` 로 옵니다.

**사전이 어긋나지 않게 하는 장치가 셋 있습니다.**

1. 한국어 사전이 키 집합의 기준이고, 나머지 셋은 `Record<MessageKey, string>` 타입입니다. 키를 빠뜨리거나 더하면 **컴파일 오류**입니다.
2. `scripts/check-i18n.ts` 가 자리표시자를 대조합니다. `{limitMb}` 를 빠뜨린 번역은 타입 검사를 통과하므로 이건 따로 잡아야 합니다. 빈 메시지도 함께 봅니다.
3. 같은 스크립트가 **사전 밖에 남은 문자열**을 훑습니다. 컴포넌트에 한글·가나·한자가 남아 있으면 실패합니다. 일부러 여러 문자를 섞어 둔 글꼴 미리보기만 `i18n-ignore` 로 예외입니다.

셋 다 `npm run check` 에 들어 있어 CI가 함께 돌립니다.

한국어는 조사가 앞말의 받침에 따라 달라져서 자리표시자 옆에 붙일 수 없습니다. `{subject}이(가)` 대신 문장을 바꿔 `{subject} — 너무 큽니다` 로 씁니다.

### 스크롤: 브라우저의 높이 한계

가상 스크롤은 `행 수 × 행 높이` 만큼의 빈 상자를 만들고 그 안에 보이는 행만 그립니다. 그런데 브라우저에는 **요소 높이의 상한**이 있습니다 — 이 웹뷰(Chromium)에서 잰 값은 **33,554,428px** 이고, 26px 행이면 약 129만 행에서 도달합니다. 넘어서면 요소는 조용히 자라기를 멈춥니다. 스크롤바가 나머지를 가리킬 방법이 없어져서, 3,840만 노드짜리 파일이 아무 표시 없이 3%짜리 파일이 됩니다.

그래서 상한을 넘으면 빈 상자를 32,000,000px에서 멈추고, 스크롤 위치를 행 범위에 **비례 대응**시킵니다(`src/lib/virtual.ts`). 스크롤바 1픽셀이 여러 행을 덮게 되는데, 3,840만 행에서 1픽셀이 1행이었던 적은 애초에 없으므로 잃는 것이 없습니다. 휠·키보드·검색 이동은 여전히 정확히 한 행씩 움직입니다. 상한 아래에서는 모든 계산이 원래의 `행 × 높이` 로 환원되므로 흔한 경우의 동작은 바뀌지 않습니다.

400만 행 CSV로 확인했습니다: 맨 아래로 끌면 3,999,959–4,000,000행이 보이고, 25%·50% 지점은 각각 100만·200만 행에 정확히 떨어집니다.

### 여는 동안의 피드백

문서를 여는 일은 디스크를 건드립니다. 그래서 탭은 **백엔드가 답하기 전에** 먼저 나타나고, 파일명과 스피너를 보여준 뒤 내용이 채워집니다. 메타데이터를 기다렸다가 탭을 만들면 그 사이가 완전히 비어 있어 앱이 멈춘 것처럼 보입니다. 같은 이유로 `open_path` 와 `doc_source_text` 는 async 커맨드입니다 — 동기 커맨드는 UI 스레드에서 실행되므로, 콜드 파일이나 네트워크 드라이브에서는 디스크가 답할 때까지 창 전체가 실제로 멈춥니다.

### 크기 조절: 두 개의 독립된 손잡이

**인터페이스 배율**은 글자와 여백을 함께 확대하고, **인터페이스 글자 크기**는 화면 요소의 글자만 바꿉니다. 둘을 진짜로 분리하려면 크롬의 글자 크기가 루트(`rem`)가 아니라 본문 크기를 따라야 해서, 인터페이스의 모든 `font-size` 를 `em` 으로 바꿨습니다. 여백은 `rem` 으로 남겨 배율만 따라갑니다. 여기에 **본문 글자 크기**(렌더된 마크다운과 JSON 트리)가 별도로 있습니다.

글꼴은 `fontdb` 로 시스템에 설치된 목록을 읽어 고릅니다 — 자유 입력은 오타가 조용히 실패하기 때문입니다. 코드 글꼴 목록은 고정폭 계열을 먼저 묶어 보여줍니다.

스캔은 설정 패널을 처음 열 때 백그라운드 스레드에서 한 번만 돕니다. 비용은 표시되는 계열 수가 아니라 **읽어야 하는 얼굴(face) 수**에 비례합니다:

```bash
cd src-tauri && cargo run --release --example fonts
```

이 기계(글꼴 117계열 / 421얼굴)에서 릴리스 **39ms**, 디버그 56ms, 얼굴당 88µs. 얼굴 2,000개짜리 환경이면 약 175ms로 외삽됩니다. 두 번째 호출부터는 캐시되어 0ms입니다.

**보조 글꼴**을 함께 지정하면 `기본, 보조, 기본 스택` 순의 폰트 스택이 만들어지는데, 브라우저는 스택을 **글리프 단위로** 훑으므로 한글이 없는 라틴 전용 글꼴을 골라도 한글만 보조 글꼴이 받습니다.

### 마크다운

`원문 → comrak(GFM) → syntect 구문 강조 → ammonia 정화 → HTML` 까지가 Rust이고, 브라우저가 꼭 필요한 세 가지만 프론트엔드에서 합니다: 상대 이미지 경로를 asset 프로토콜로 바꾸기, Mermaid 렌더, KaTeX 조판 (`src/lib/components/markdown/enhance.ts`).

구문 강조는 인라인 스타일이 아니라 **클래스 기반**이고, 라이트/다크 두 스타일시트를 미리 만들어 둡니다. 그래서 테마를 바꿔도 문서를 다시 렌더링하지 않습니다.

URL과 클립보드로 들어온 문서도 있으므로 ammonia 정화는 선택이 아닙니다. `<script>`·`onerror`·`javascript:` 는 `markdown.rs` 의 테스트로 막혀 있습니다.

### 보안 경계

- 프론트엔드에는 파일시스템 권한이 없습니다 (`src-tauri/capabilities/default.json` 에 `fs:*` 없음). 파일 읽기는 전부 Rust 커맨드를 거칩니다.
- asset 프로토콜 스코프는 비어 있는 채로 시작하고, **마크다운 문서를 열 때 그 문서의 디렉터리만** 추가됩니다. 트리·표 문서는 로컬 자원을 참조하지 않으므로 스코프를 넓히지 않습니다.
- 외부 링크는 웹뷰에서 이동하지 않고 시스템 브라우저로 넘깁니다.
